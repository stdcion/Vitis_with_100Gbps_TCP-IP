# Почему ядра не работают на плате: причина найдена

Состояние на 17.08.2026. Файл заменяет предыдущую версию целиком: та называла
причиной форму стадий (`while(true)`), и это **опровергнуто симуляцией**.

Предыдущий контекст (измерение задержки, врезки, тестбенчи) —
[latency_session_handoff.md](latency_session_handoff.md), он верен во всём, что
касается врезок и методики.

## Причина

`ap_continue` стадии в dataflow-регионе — это `ap_sync_done`, логическое **И по
всем 14 стадиям** региона:

```verilog
// dual_echo_core.v:1337
assign ap_sync_done = (tie_off_udp_U0_ap_done & ... &
                       dual_echo_rx_drain_U0_ap_done & ... );
// :1335
assign ap_sync_continue = (ap_sync_done & ap_continue);
// :1371
assign dual_echo_listen_U0_ap_continue = ap_sync_continue;
```

Внутри стадии `ap_done_reg` сбрасывается ТОЛЬКО по `ap_continue`
(`dual_echo_listen.v:303`), а при `ap_done_reg == 1` конвейер заблокирован
(`:609`, `ap_block_pp0_stage1_01001`).

**Следствие:** одна стадия, не выставившая `ap_done`, замораживает все
остальные после ОДНОГО прохода. Этот единственный проход расходуется сразу после
снятия сброса, когда `enable` ещё 0 и стадия уходит по ветке
`if (!enable) { portState = 0; return; }`. Поздний `enable=1` доходит до порта
проводом, но реагировать на него уже нечем.

Отсюда наблюдаемое на плате: `enable` читается обратно как 1, а
`listenAttempts=0`, `portState=0`, все стадии молчат.

Кандидат на стадию-виновника — `dual_echo_rx_drain`: автомат ждёт данных в
`rxSessionFifo`; их кладёт `rx_notify`, который ждёт notification от стека; стек
молчит, пока listen не открыл порт. Круг замкнут. **Не доказано** — см. «Что
осталось».

## Чем это доказано

`kernel/user_krnl/hls_dual_echo_krnl/src/hdl/tb/`, запуск:

```bash
source /tools/Xilinx/Vivado/2022.1/settings64.sh
cd kernel/user_krnl/hls_dual_echo_krnl/src/hdl/tb
./run_sim.sh          # оба тестбенча
./run_sim.sh listen   # только стадия (нужен make user_ip)
./run_sim.sh ctrl     # только обёртка (csynth не нужен)
```

`tb_listen_start` симулирует СГЕНЕРИРОВАННЫЙ HLS-RTL, то есть железо из
битстрима. Результаты (все зелёные на 17.08):

| фаза | что проверяет | результат |
|---|---|---|
| 1 | `enable=0` | 0 записей, 2499 проходов — стадия жива |
| 2 | поздний `enable=1` | запрос уходит за <100 тактов |
| 3 | молчащий стек | 2 записи, 1502549 проходов — повтор по таймауту работает |
| 4 | `TREADY=0` | 1 попытка, стадия встаёт |
| 6 | `ap_continue` от чужих стадий | **1 проход, 1 запись** |
| 7 | поздний `enable` + `ap_continue` от чужих | **att=0, state=0, 0 записей** |

Фазы 3 и 6 отличаются РОВНО одним сигналом — `ap_continue`. 1502549 проходов
против одного. Фаза 7 воспроизводит лог платы дословно.

`tb_dual_echo_ctrl` симулирует НАШУ обёртку (настоящие
`dual_echo_control_s_axi.v` + `hls_dual_echo_krnl_wrapper.sv`, ядро и VIO —
заглушки). Все проверки зелёные: `enable`, записанный по `0x10`, доходит до порта
`enableA` ядра; телеметрия возвращается; адресная карта `DE_OFF_*` совпадает.

## Что ОПРОВЕРГНУТО — не проверять заново

| Гипотеза | Чем опровергнута |
|---|---|
| Скаляры защёлкиваются без `s_axilite`, логика видит 0 | `enableB` читается комбинационно (`listen.v:676`); поздний `enable` доходит (фаза 2). **ЗНАЧИТ HDL-ОБЁРТКИ БЫЛИ НЕ НУЖНЫ** |
| Стадии без `while(true)` не годятся для непрерывной работы | 1502549 проходов (фаза 3). Апстримный `listen_port_handler` тоже без цикла (`communication.hpp:728`) |
| `ap_start = 1'b1` не даёт сбросить `ap_sync_reg`, отсюда один проход | Опровергнуто фазами 1 и 3. Механизм `ap_start` у нас и у работающего `recv` ИДЕНТИЧЕН (`recv.v:662` против `core.v:1373`) |
| `static` в dataflow теряется (HLS 214-111 × 8) | В `core` их нет вообще; внутри стадии это регистры со сбросом только по `ap_rst` (`listen.v:383`) |
| `ap_ctrl` не пишется | Пишется (`jtag_ctrl.tcl:1477`), и на `enable` не влияет (фаза 4 `tb_dual_echo_ctrl`) |
| Оба CMAC на одном сайте | В актуальном логе `1208_03.txt` конфликта нет (был в старом `last_impl.txt`) |
| В битстриме чужое ядро | В BD стоит `hls_dual_echo_krnl_1` по адресу `0x10000` = `ouch_base_user 1` (`1208_03.txt:2014`) |
| Обёртка рвёт `enable` | `tb_dual_echo_ctrl` — всё зелёное |
| Закрытый `TREADY` — причина | Фаза 4 даёт `att=1`, а плата показывает 0 |
| Врезки `axis_net_*` висят неподключёнными | У обёртки `dual_echo` их нет вообще (только у `probe`) |

## Что осталось

**Назвать стадию, которая не выдаёт `ap_done`.** В фазе 6/7 это мой сигнал
`other_stages_done`, а не настоящая стадия. Нужен тестбенч на весь
`dual_echo_core` (221 порт) со всеми 14 стадиями: он покажет, кто держит
`ap_sync_done`. Заглушки для такого теста генерируются скриптом из
сгенерированного RTL — см. шапку `stub_hls_dual_echo_krnl_ip.v`, там описан
приём.

**Направления лечения** (после того, как виновник назван):

1. Убрать `disable_start_propagation` — возможно, изменит схему `ap_sync`.
2. Вернуть `s_axilite` + `ap_ctrl_hs` + `auto_restart` (`0x81`), удалить
   `src/hdl/` и `package_*.tcl`. Это делает ядро таким же, как доказанно
   работающий `hls_recv_krnl` (2 файла против 8). `auto_restart` даёт импульсы
   `ap_start`, которые сбрасывают `ap_sync_reg`. ОГОВОРКА: `ap_sync_done` — И по
   всем стадиям, поэтому одного `auto_restart` может не хватить.
3. Развязать круг `rx_drain` → `rx_notify` → стек: чтобы `rx_drain` выдавал
   `ap_done` при пустых FIFO.
4. `while(true)` в стадиях — сработает (стадия не выдаёт `ap_ready`, значит не
   блокируется), но утяжеляет логику. При WNS +0.03 и потолке 165 МГц это риск,
   и это НЕ первый выбор.

Для `hls_echo_probe_dual_krnl` причина, скорее всего, та же: у него `epd_core` с
тем же `DATAFLOW disable_start_propagation` и 4 стадии + заглушки. Проверять тем
же способом.

## Урок метода

Тестбенч дважды давал ложноотрицательный результат из-за длительности прогона:
`LISTEN_TIMEOUT` равен миллиону, причём в ПРОХОДАХ стадии, а не в тактах — при
II=2 это ~2 млн тактов. Прогоны на 4 000 и на 1.2 млн тактов «опровергали»
верную гипотезу.

Правило: длительность считать в проходах стадии, умножая на фактический II,
измеренный этим же тестом; константы брать из сгенерированного RTL, а не из
`.cpp`.

Второе: тестбенч на стадию отдельно НЕ ВИДИТ дефектов её окружения. Фазы 1-3
были зелёными полтора часа и вводили в заблуждение, пока `ap_continue` был
константой `1'b1` вместо `ap_sync_done`. Модель окружения надо строить по RTL
построчно, а расхождения выписывать явно — иначе «оптимистичнее железа»
превращается в «проверяет не то».

* `network_krnl` и bringup стеков (`echo_bringup_dual`) — проверены на плате;
* врезки: impl прошёл, `WNS +0.0306`, битстрим собран (13.08);
* тесты: `run_sim.sh` в `hls_dual_echo_krnl` (2 тестбенча) и в
  `hls_echo_probe_dual_krnl` (76 проверок), `run_csim.tcl`,
  `test_epd_taps.tcl` (51), `test_net_frame_filter.py`;
* физика: пинги идут, ARP работает, IP защёлкивается. Второй Ethernet в момент
  снятия VIO был не подключён — `rx_pkg_counter=0` на канале 1 этим и
  объясняется, это не дефект.
