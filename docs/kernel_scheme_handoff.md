# Почему ядра не работают на плате: причина найдена

Состояние на 17.08.2026. Файл заменяет предыдущую версию целиком: та называла
причиной форму стадий (`while(true)`), и это **опровергнуто симуляцией**.

Предыдущий контекст (измерение задержки, врезки, тестбенчи) —
[latency_session_handoff.md](latency_session_handoff.md), он верен во всём, что
касается врезок и методики.

> **ЧАСТИЧНО УСТАРЕЛО (20.08).** Захват Wireshark сравнил ДВА ЯДРА на одной
> плате и локализовал дефект точнее всего, что здесь есть: `recv` даёт SYN-ACK
> за 69 мкс на 7001 и RST за 64-66 мкс на закрытых портах, `dual_echo` на том же
> 7001 — ТИШИНУ. Тишина вместо RST означает, что порт зарегистрирован, а SYN
> роняется в `rx_engine` при промахе lookup (`:914`, авторский TODO на `:926`).
>
> Опровергнуты и не подлежат перепроверке: `0.0.0.0`, DDR (таблица сессий —
> BRAM), `myIpAddress` у ARP, барьер `ap_sync_done`, доставка `ap_start`,
> `static` при `auto_restart`, гонка инициализации.
>
> Текущий опыт — [recv_dual_control_experiment.md](recv_dual_control_experiment.md).

## Причина

`ap_continue` стадии в dataflow-регионе — это `ap_sync_done`, логическое **И по
всем 14 стадиям** региона:

```verilog
// dual_echo_core.v:1337
assign ap_sync_done = (tie_off_udp_U0_ap_done & ... &
                       dual_echo_rx_drain_U0_ap_done & ... );
// :1335
assign ap_sync_continue = (ap_sync_done & ap_continue);
// :1371
assign dual_echo_listen_U0_ap_continue = ap_sync_continue;
```

Внутри стадии `ap_done_reg` сбрасывается ТОЛЬКО по `ap_continue`
(`dual_echo_listen.v:303`), а при `ap_done_reg == 1` конвейер заблокирован
(`:609`, `ap_block_pp0_stage1_01001`).

**Следствие:** одна стадия, не выставившая `ap_done`, замораживает все
остальные после ОДНОГО прохода. Этот единственный проход расходуется сразу после
снятия сброса, когда `enable` ещё 0 и стадия уходит по ветке
`if (!enable) { portState = 0; return; }`. Поздний `enable=1` доходит до порта
проводом, но реагировать на него уже нечем.

Отсюда наблюдаемое на плате: `enable` читается обратно как 1, а
`listenAttempts=0`, `portState=0`, все стадии молчат.

Кандидат на стадию-виновника — `dual_echo_rx_drain`: автомат ждёт данных в
`rxSessionFifo`; их кладёт `rx_notify`, который ждёт notification от стека; стек
молчит, пока listen не открыл порт. Круг замкнут. **Не доказано** — см. «Что
осталось».

## Чем это доказано

`kernel/user_krnl/hls_dual_echo_krnl/src/hdl/tb/`, запуск:

```bash
source /tools/Xilinx/Vivado/2022.1/settings64.sh
cd kernel/user_krnl/hls_dual_echo_krnl/src/hdl/tb
./run_sim.sh          # оба тестбенча
./run_sim.sh listen   # только стадия (нужен make user_ip)
./run_sim.sh ctrl     # только обёртка (csynth не нужен)
```

`tb_listen_start` симулирует СГЕНЕРИРОВАННЫЙ HLS-RTL, то есть железо из
битстрима. Результаты (все зелёные на 17.08):

| фаза | что проверяет | результат |
|---|---|---|
| 1 | `enable=0` | 0 записей, 2499 проходов — стадия жива |
| 2 | поздний `enable=1` | запрос уходит за <100 тактов |
| 3 | молчащий стек | 2 записи, 1502549 проходов — повтор по таймауту работает |
| 4 | `TREADY=0` | 1 попытка, стадия встаёт |
| 6 | `ap_continue` от чужих стадий | **1 проход, 1 запись** |
| 7 | поздний `enable` + `ap_continue` от чужих | **att=0, state=0, 0 записей** |

Фазы 3 и 6 отличаются РОВНО одним сигналом — `ap_continue`. 1502549 проходов
против одного. Фаза 7 воспроизводит лог платы дословно.

`tb_dual_echo_ctrl` симулирует НАШУ обёртку (настоящие
`dual_echo_control_s_axi.v` + `hls_dual_echo_krnl_wrapper.sv`, ядро и VIO —
заглушки). Все проверки зелёные: `enable`, записанный по `0x10`, доходит до порта
`enableA` ядра; телеметрия возвращается; адресная карта `DE_OFF_*` совпадает.

## Что ОПРОВЕРГНУТО — не проверять заново

| Гипотеза | Чем опровергнута |
|---|---|
| Скаляры защёлкиваются без `s_axilite`, логика видит 0 | `enableB` читается комбинационно (`listen.v:676`); поздний `enable` доходит (фаза 2). **ЗНАЧИТ HDL-ОБЁРТКИ БЫЛИ НЕ НУЖНЫ** |
| Стадии без `while(true)` не годятся для непрерывной работы | 1502549 проходов (фаза 3). Апстримный `listen_port_handler` тоже без цикла (`communication.hpp:728`) |
| `ap_start = 1'b1` не даёт сбросить `ap_sync_reg`, отсюда один проход | Опровергнуто фазами 1 и 3. Механизм `ap_start` у нас и у работающего `recv` ИДЕНТИЧЕН (`recv.v:662` против `core.v:1373`) |
| `static` в dataflow теряется (HLS 214-111 × 8) | В `core` их нет вообще; внутри стадии это регистры со сбросом только по `ap_rst` (`listen.v:383`) |
| `ap_ctrl` не пишется | Пишется (`jtag_ctrl.tcl:1477`), и на `enable` не влияет (фаза 4 `tb_dual_echo_ctrl`) |
| Оба CMAC на одном сайте | В актуальном логе `1208_03.txt` конфликта нет (был в старом `last_impl.txt`) |
| В битстриме чужое ядро | В BD стоит `hls_dual_echo_krnl_1` по адресу `0x10000` = `ouch_base_user 1` (`1208_03.txt:2014`) |
| Обёртка рвёт `enable` | `tb_dual_echo_ctrl` — всё зелёное |
| Закрытый `TREADY` — причина | Фаза 4 даёт `att=1`, а плата показывает 0 |
| Врезки `axis_net_*` висят неподключёнными | У обёртки `dual_echo` их нет вообще (только у `probe`) |

### hls_echo_probe_dual_krnl — готов к сборке

`ap_ctrl_hs` БЕЗ `s_axilite`: регистры и все восемь таймстемпов остаются в
`probe_control_s_axi.v`, `ap_start` приходит портом. HLS такую конфигурацию
принимает. Врезки, единая шкала времени и 76 проверок тестбенчей не тронуты.
Цена: `*_hw.h` не генерируется, карту (`EPD_OFF_*` против `localparam`) держим
синхронно вручную.

Найдено ДВА дефекта, второй прятался за первым — оба давали `connAttempts=0/1`
и тишину:

1. **барьер `ap_sync_done`** — снят переходом на `ap_ctrl_hs`;
2. **`epd_client_connect` не выходил из `WAIT_STATUS`** — единственным условием
   выхода было «пришёл `open_status`». Стек молчит (на старте сервер ещё не открыл
   порт) → автомат стоит навсегда, `retryTimer` не тикает. Добавлена ветка по
   таймауту, как в `epd_server_listen`, где эту дыру закрыли раньше.

| | до | после |
|---|---|---|
| `open_connection` (клиент) | 1 | **9** за 3 млн тактов |
| `listen_port` (сервер) | 1 | 1 — правильно, порт держится |
| Тестбенчи обёртки | — | ALL GREEN (фильтр, врезки, ctrl) |

Стробы таймстемпов переведены с `ap_vld` на шину (`tvalid & tready & tlast`):
`ap_vld` приходит на `ap_done` прохода, и при `ap_ctrl_hs` это давало бы
систематическую ошибку между половинами в NET_FWD/NET_REV — невидимую, потому что
баланс сходится.

Осталось: `bd` + `impl`, прошить, `epd_measure`.

## 18.08: что проверено ПОСЛЕ платы и что осталось

Симптом после снятия барьера: `portState=2(OPEN)`, ICMP ходит, `ap_idle` упал,
но SYN клиента остаётся без ответа **и без RST**. Отсутствие RST означает, что
порт для стека реально открыт (на закрытый 7005 RST приходит — проверено).

`portState=2` не наша догадка: он ставится только после чтения `success` из
`s_axis_tcp_port_status`, то есть **TOE подтвердил listen**. Значит проблема
после подтверждения порта.

### Гипотеза про DDR — ОПРОВЕРГНУТА

Была основная: таблица сессий TOE живёт в DDR по `axi00_ptr0`/`axi01_ptr0`,
`network_set_buffers` пишет `0x0`/`0x40000000`, и если сегмент начинается не с
нуля — TOE пишет в пустоту. Проверено по `hw.xsa` платформы и её `ulp.bd`:

| проверка | результат |
|---|---|
| MIG/калибровка | зелёная, все pass (сообщил пользователь) |
| `DDR4_AXI_ADDR_WIDTH` | 34 бита -> `0x0..0x3_FFFF_FFFF`, оба указателя внутри |
| наш `ddr4_c3` vs платформенный `ddr4_mem00` | тот же VLNV `ddr4:2.2`, та же `smartconnect` с `NUM_CLKS=2`, оба задают только `AxiAddressWidth`, остальное из board file |
| ECC | у платформы в BD тоже не отключён — расхождения нет |
| перекрытие `0x0` и `0x40000000` | 1 ГБ разнос, таблицы — килобайты |

Адреса печатать всё равно полезно (шаг `bd` теперь это делает), но **причина не
здесь**. Гипотезу закрыть, заново не проверять.

### Врезки, sc=, физика — тоже не здесь

`config_sp` сверен построчно с рабочим `hls_recv_krnl`: 18 связей на канал, оба
направления, все на месте, различие только в суффиксах `_a`/`_b`.

### Что осталось и куда смотреть — ДВА НЕЗАВИСИМЫХ КАНДИДАТА

**(1) ВЛОЖЕННЫЙ DATAFLOW.** `#pragma HLS DATAFLOW` стоит ДВА раза: на
`hls_dual_echo_krnl` (`:778`) и внутри `dual_echo_core` (`:492`). То есть регион
не один, а вложенный, и `dual_echo_core` — сам стадия внешнего региона со своими
`ap_start`/`ap_done`/`ap_continue`.

Свидетельство того, что это не безобидно: `HLS 200-656` про
`ap_ctrl_none или without start propagation` **остался и после перехода на
`s_axilite + ap_ctrl_hs`** (лог `1708_full.txt:742,900` — 10 вхождений, ровно
`dual_echo_listen` и `dual_echo_rx_notify`, по два экземпляра каждой). Если бы
внешний `ap_start` доходил до стадий, предупреждение должно было исчезнуть.
Правдоподобное чтение: `auto_restart` перезапускает ВНЕШНИЙ регион, а внутренний
барьер `dual_echo_core` живёт своей жизнью.

Осторожно: измерение `writes 1/1 -> 10/10` получено на `tb_core_ap_done`, который
подаёт `ap_start` **прямо в `dual_echo_core`**, минуя внешний регион. То есть тест
доказал, что внутренний регион оживает от импульса — но НЕ доказал, что импульс
до него доходит в реальном дизайне. Это та же ошибка метода, что в уроке про
`tie_off`: измеряли не то место.

*Как проверить дешевле всего:* в сгенерированном `hls_dual_echo_krnl.v` (на
сборочной машине) посмотреть, чем управляется `dual_echo_core_U0_ap_start` — если
это `ap_sync_continue` внешнего региона, а не импульс от `ap_start`, гипотеза
подтверждена. Дальше — убрать внутренний `#pragma HLS DATAFLOW` из
`dual_echo_core`, оставив один регион на верхнем уровне.

**(2) `return` В `dual_echo_rx_notify`.** Две штуки (`s_axis_tcp_notification.empty()`
и `rxSessionFifo.full()`), и это ровно та стадия, которая должна принять
уведомление о данных. Апстрим здесь устроен принципиально иначе:
`recvData_handshake` — `do/while` по счётчику байт, из него не выходят. См.
[[hls-early-return-stops-stage]]: правило было выписано, но в этой стадии не
применено. `notifications` в телеметрии — прямой индикатор, растёт ли она вообще.

### 18.08, probe на плате: ВЛОЖЕННЫЙ DATAFLOW ПОДТВЕРЖДЁН

Прогон `epd_*` (три `epd_status` с десятками секунд между ними) разделил двух
кандидатов без пересборки. Кандидат «early return в rx_notify» отпадает: он не
объяснил бы `timeouts=0`.

| наблюдение | что следует |
|---|---|
| `network_krnl[1,2] ap_ctrl=0x81`, **`ap_done=0`** | стеки крутятся, регион не финиширует — как и должно быть |
| `epd ap_ctrl=0x83`, **`ap_done=1`** | ядро ФИНИШИРОВАЛО и залипло в done. Прямой контраст со стеком на той же плате |
| `listen: attempts=1 state=2(OPEN)` | listen отработал ОДИН раз, успешно |
| `connAttempts=1` в трёх замерах | ожидалось ~4700 за 10 с (`retryDelay`=100000 проходов × 3.5 такта / 165 МГц = 2.1 мс). Расхождение на ЧЕТЫРЕ ПОРЯДКА |
| **`timeouts=0`** | решающее: не считаются даже таймауты. Значит стадии не проходят циклы ВООБЩЕ — это не «работают, но данных нет» |

`ap_done=1` при `auto_restart` и есть подпись вложенного региона: внешний
DATAFLOW отработал один проход и встал, `auto_restart` его не перезапускает,
потому что `disable_start_propagation`-семантика вложенности не даёт импульсу
дойти до внутренних стадий. Внутренний `epd_core` при этом исправен — что и
показывал `tb_core_ap_done`, подавая `ap_start` прямо в него.

**Оба ядра больны одним и тем же:** `#pragma HLS DATAFLOW` дважды —
probe `:1211` и `:925`, dual_echo `:778` и `:492`.

Правка одна и та же: убрать ВНУТРЕННИЙ pragma из `epd_core`/`dual_echo_core`,
оставив один регион на верхнем уровне. Стадии не меняются.

Проверка правки до платы: в сгенерированном `hls_*_krnl.v` посмотреть, чем
управляется `*_core_U0_ap_start`, и что `HLS 200-656` исчез из лога csynth.

### 18.08, tb_top_start на probe: плата воспроизведена в симуляции

Прогон на ТЕКУЩЕМ RTL (том, что в неработающем битстриме):

```
phase 1 (один импульс):   writes a=1 b=1, core ap_start seen=1, ap_done seen=1
phase 2 (ap_start=1, 1M): writes a += 2, b += 0
                          core ap_idle=1  ПРИ ПОДНЯТОМ ap_start
                          top ap_done seen=1, сейчас 0
```

Симптом платы воспроизведён: регион делает единицы проходов вместо сотен тысяч.
Тестбенч, подающий `ap_start` в top, показывает то, чего `tb_core_ap_done` увидеть
не мог — и это подтверждает, что слепой участок был именно там.

**НО ПРЕДСКАЗАНИЕ СОШЛОСЬ ЛИШЬ НАПОЛОВИНУ, и это важнее вердикта.** Ожидалось:
`writes` единицы **и** `ap_done` top залипает в 1. Первое сошлось. Второе — нет:
`top ap_done` снялся (`сейчас 0`), то есть внешний регион перезапускается, и всё
равно `core` стоит в `ap_idle=1`.

Три факта, которые чистая вложенность не объясняет:

| факт | что из него следует |
|---|---|
| `core ap_start seen=1`, phase 1 прошла | импульс ДОХОДИТ до core, а не блокируется |
| `core ap_idle=1` при поднятом `ap_start` | core вернулся в idle и не стартует повторно |
| `writes a += 2`, `b += 0` | половины ведут себя РАЗНО — при общем барьере были бы симметричны |

Асимметрия a/b — самое неудобное для гипотезы: внешний барьер один на обе
половины. Значит либо кроме вложенности есть вторая причина, либо дело не в ней,
а в том, что `ap_start` не подаётся ПОВТОРНО.

**Поэтому в тест добавлен разбор**, различающий три случая по приросту
`core ap_start seen` за phase 2: «больше не подаётся» (вложенность), «стартует
много раз, шина молчит» (барьер внутри core или early return), «стартует единицы
раз» (внешний регион завершается и перезапускается вместо непрерывной работы).

**И добавлен `scripts/vivado/show_core_start.sh`** — три строки RTL вместо
догадок: чем именно питается `.ap_start(...)` у инстанса core. Если там
`ap_sync_continue` — вложенность; если `ap_start` — гипотезу менять.

Правку внутреннего pragma **делать после** этих двух измерений: если причина в
неповторяющемся `ap_start`, удаление pragma её не устранит.

### 18.08, ВЕЧЕР: ГИПОТЕЗА О ВЛОЖЕННОСТИ ОПРОВЕРГНУТА. Тракт управления исправен

Два прогона на сборочной машине закрыли вопрос, и ответ обратный ожидаемому.

**Строка 823 сгенерированного `hls_echo_probe_dual_krnl.v`:**

```verilog
assign epd_core_U0_ap_continue = 1'b1;
```

`ap_continue` внутреннего региона — **константная единица**. Внешний DATAFLOW
ничего не перехватывает, вложенность НИ ПРИ ЧЁМ. Правка, к которой всё вело
(убрать внутренний pragma), не дала бы ничего.

**Числа phase 2 при поднятом `ap_start`:**

| измерено | значит |
|---|---|
| `core ap_start seen += 999999` | импульс приходит КАЖДЫЙ такт |
| `core ap_done seen += 285713` | регион проходит цикл 285 тыс. раз; 1e6/285713 = **3.50 такта на проход** |
| `core ap_idle = 0` | регион не простаивает |
| `writes_a += 2` | стадия пишет дважды |

Барьер `ap_sync_done` СРАБАТЫВАЕТ (иначе `ap_done` не росло бы). Стадии получают
`ap_continue` и идут. Диагноз «стадии заперты барьером» тоже неверен.

**А два — это ПРАВИЛЬНОЕ число.** `retryDelay = 100000` ПРОХОДОВ × 3.50 такта =
350 тыс. тактов на попытку, то есть за 1 млн тактов ровно 2-3 записи. Сверка с
измерением 17.08: там было 9 за 3 млн (при `ap_start` прямо в core), здесь 2×3=6
за 3 млн — тот же порядок.

**Ошибка была в ПОРОГЕ ТЕСТА, а не в ядре.** Порог «>10 записей за 1 млн тактов»
физически недостижим при `retryDelay=100000` и объявлял исправный тракт сломанным.
Это ТРЕТИЙ раз, когда длительность считалась в тактах вместо проходов × II —
см. «Урок метода» ниже; правило было выписано и снова не применено, теперь уже
не к длине прогона, а к ожидаемому результату.

**Исправлено:** порог вычисляется из таймаута, а `RETRY_DELAY` читается из `.cpp`
(`retryDelay` у probe, `LISTEN_TIMEOUT` у dual_echo — оба 100000), а не дублируется
в тестбенче. Тест печатает `ARIFMETIKA: passes, такта/проход, ожидаем ~N записей`
и сверяет с ожиданием. На ваших числах: ожидаем 2, факт 2. Проверок стало две —
«регион не заперт» (`passes > 1000`) и «записи соответствуют `RETRY_DELAY`».
Вердикт больше не утверждает вложенность и прямо велит смотреть
`show_core_start.sh`.

### ЧТО ЭТО ЗНАЧИТ ДЛЯ ПЛАТЫ

Тракт управления probe **исправен в симуляции**: импульс доходит, регион крутится,
стадии пишут с темпом, заданным таймаутом. Но на плате `connAttempts=1` и не
растёт, хотя должен был дать тысячи за десятки секунд.

Симуляция и плата РАСХОДЯТСЯ. Значит причина в том, чего в симуляции нет:

1. **`s_axis_*` в тестбенче молчат** (`TVALID=0`), а на плате стек отвечает.
   Стадия могла встать, ПОЛУЧИВ ответ — например `open_status` с отказом,
   которого тестбенч не подаёт.
2. **`m_axis_*_TREADY=1` всегда.** На плате `network_krnl` может не принимать —
   тогда стадия блокируется на записи. Проверяется подачей `TREADY=0`.
3. **`ap_ctrl` на плате = 0x83, а не 0x81.** `ap_done=1` держится — в симуляции
   top `ap_done` снимался. Разницу надо объяснить.

Следующий тест должен моделировать ОТВЕТЫ стека, а не его молчание.

### 19.08: tb_stack_reply -- ЯДРО ОБРАБАТЫВАЕТ ОТВЕТЫ СТЕКА ВЕРНО

Закрыта последняя дыра: ни один из пяти прежних тестбенчей не поднимал `TVALID`

| 1 | стек молчит | `open_writes += 2` — повторы по таймауту идут |

**ТРИ ЦИФРЫ, КОТОРЫЕ ВАЖНЕЕ ВЕРДИКТА:**

3. **В фазе 4 сосед БЫСТРЕЕ клиента: 1.25 такта против 6.67** (`server ap_done

### ДВА ДЕФЕКТА В САМОМ ТЕСТЕ (найдены и исправлены)

**`ap_continue` не был подключён.** Первый прогон дал `open_writes += 0` во ВСЕХ
фазах, включая базис, — при том что `tb_top_start` на том же RTL давал `+= 2`.
Тест противоречил тесту, значит сломан тест. `ap_continue` -- обычный `input`, он
не попал ни в одну ветку раскладки и получил НОЛЬ, который держит `ap_done_reg`
каждой стадии и запирает регион. Подпись, которую надо было увидеть сразу:
`ap_done += 1000000` за 1M тактов — это не «тикает миллион раз», это СТОИТ В
ЕДИНИЦЕ; при `II=1, Depth=3` такого не бывает. Исправлено таблицей
`BLOCK_PROTO_IN` плюс ловушка: любой вход `ap_*` вне таблицы валит генератор.

**Фаза 5 была зелёной СЛУЧАЙНО.** Она печатала «server ne poprosil port za 2M
taktov» и одновременно `portState=2`. Противоречие: порт не может открыться без
запроса. Причина -- снимок `listen_writes` брался через `repeat(100)` ПОСЛЕ снятия
сброса, а запрос уходит в первые же такты, внутри этого окна. Двойка досталась от
предыдущих фаз, а не от `reply_port_status`. Исправлено: снимок ДО сброса, плюс
проверка `portState != 2` до ответа — без замера «до» нельзя утверждать, что
двойку сделал ответ стека.

### ЧТО ОСТАЛОСЬ: расхождение сузилось до трёх пунктов

Симуляция теперь покрывает и молчащий стек, и отвечающий, и закрытый `TREADY`.
Ядро во всех случаях исправно. На плате -- `connAttempts=1` и тишина. Различия,
которых в симуляции по-прежнему НЕТ:

1. **`ap_ctrl=0x83` на плате** -- `ap_done` держится. В симуляции регион
   финиширует и перезапускается. Что именно на плате не даёт снять `ap_done` --
   не проверено ни одним тестом.
2. **Реальные тайминги стека.** Тестбенч отвечает мгновенно; TOE отвечает через
   микросекунды и может прислать ответ, когда стадия уже в другом состоянии.
3. **Второй канал и врезки.** Все тесты гоняют `epd_core` в одиночку. На плате
   между ядром и CMAC стоят `net_frame_filter` и таймстемп-логика.

Следующий шаг -- `epd_dump` на плате (готов, коммит 788ffb5): он снимет
`ap_ctrl`, оба замера счётчиков и VIO до/после подключения за один запуск.
Пункт 1 проверяется только на железе.

### 19.08, сравнение с iperf_client: ДВА РАЗЛИЧИЯ, оба проверяемы офлайн

Сравнение делалось с `hls_recv_krnl`, а он **только сервер**. probe — ещё и
клиент, и клиентскую половину сравнивать было не с чем. Нашёлся референс:
`iperf_client.cpp` — клиент, который **работает на этом железе**.

**РАЗЛИЧИЕ 1: upstream ЖДЁТ перед первым `open_connection`.**

```cpp
// communication.hpp:68, внутри openConnections()
volatile int wait_counter = 0;
for (int i = 0; i < 100; ++i) { wait_counter++; }
```

Единственное такое место во всём upstream. Комментария нет, но `volatile` не даёт
HLS выбросить цикл — значит поставлено намеренно. Смысл: не писать
`open_connection`, пока стек не готов. У probe такой задержки нет, клиент пишет
сразу после сброса.

**РАЗЛИЧИЕ 2: iperf читает шину статуса ОТДЕЛЬНОЙ стадией.**

| | как читается `open_status` |
|---|---|
| iperf (работает) | `openStatus_handler` — отдельная стадия, опустошает шину **каждый проход** в свой FIFO; FSM читает из FIFO и шину не трогает |
| probe | `epd_client_connect` читает шину **сам** и **только в `WAIT_STATUS`** |

Следствие: если ответ стека придёт, когда автомат не в `WAIT_STATUS` (в
`RETRY_WAIT` или уже в `DONE`), у iperf он всё равно будет прочитан, а у нас
останется в шине.

**Почему симуляция этого не поймала.** Все прежние фазы отвечали МГНОВЕННО, то
есть всегда попадали в `WAIT_STATUS`. Промахнуться по состоянию было невозможно
по построению. На плате TOE отвечает через микросекунды.

Добавлена **фаза 4b**: ответ подаётся через `RETRY_DELAY × 4` тактов, когда
автомат гарантированно ушёл из `WAIT_STATUS`. Различает два исхода явно —
`PODHVACHEN` (записи встали, ответ обработан) против `POTERJAN` (записи
продолжаются, слово никто не взял).

Проверено, что стадии `epd_client_traffic` и `epd_server_echo` читают шины РАЗНЫХ
половин (`_a` против `_b`) — конфликта двух читателей одной шины нет. Заглушки
`tie_off_*` тоже корректны: `port_status_a` вычитывается, `listen_port_a` не
пишется никогда.

### 19.08: фаза 4b ПРОГНАНА -- поздний ответ подхватывается, но темп повторов не сходится

10 проверок, все зелёные. Числа фазы 4b:

```
after 400000 cycles of waiting: open_writes=10
after the late reply: open_writes += 0, ap_done += 85715
ANALYSIS: writes stopped -> late reply WAS PICKED UP
```

**Поздний ответ обрабатывается верно.** Ответ подан через 400 тыс. тактов, когда
автомат гарантированно вышел из `WAIT_STATUS`; после него записи прекратились --
значит клиент перешёл в `DONE`, то есть слово было прочитано. Гипотеза «шина
читается только в `WAIT_STATUS`, поздний ответ теряется» -- **опровергнута**.

`ap_done += 85715` за 200 тыс. тактов = **2.33 такта на проход**, до второго знака
совпадает с фазами 1-3. Стадия идёт штатно.

Оговорка: вывод «поздний ответ подхватывается» был записан в предыдущей версии
этого раздела ДО прогона, из одного слова в ответе пользователя, и оказался верен
**случайно**. Совпадение не оправдывает метод -- см. четвёртый урок ниже.

### АНОМАЛИЯ ЗАКРЫТА: её не было, ошибка была в моём вычитании

Предыдущая версия этого раздела утверждала, что темп повторов расходится в 6 раз
(500 тыс. тактов на попытку в фазе 1 против 80 тыс. в 4b) и что «объяснения нет».
Тест дополнили, чтобы он печатал прирост сам. Результат:

```
during 400000 cycles of waiting: open_writes += 1 (total 10)
retry rate: 400000 cycles per attempt (phase 1 gave 500000)
```

**Прирост за фазу 4b -- ОДНА запись, не пять.** Расхождение темпа 1.25x, то есть
округление на единичных событиях.

Откуда взялись «пять»: я сложил приросты фаз (2+0+3+0 = 5) и вычел из накопленного
10. Но между фазами стоят СБРОСЫ (`ap_rst` перед 3, 4, 4b), и после каждого
автомат заново проходит `IDLE` -> запись. Эти записи не попали ни в один прирост:
они случились после снимка `w0` предыдущей фазы и до снимка следующей. Фактически
к началу 4b накопилось 9.

Сходимость с `retryDelay`: 100000 x ~4.3 такта на инкремент таймера = 430 тыс.
тактов -- попадает между измеренными 400 тыс. и 500 тыс.

**Урок, пятый.** Прошлые четыре: арифметика в проходах, а не тактах; измерять на
живой шине, а не на заглушке; модель окружения строить по RTL; не записывать вывод
без чисел. Этот -- **не вычитать накопленные счётчики руками**. Разность двух
снимков должен печатать тест, потому что между снимками происходит то, чего в
голове не учтёшь: здесь это были сбросы между фазами.

## 19.08, ВЕЧЕР: ЧТО ПОКАЗАЛ epd_dump (маска -- ЛОЖНЫЙ СЛЕД, см. ниже)

### ЛОЖНЫЙ СЛЕД: МАСКА ПОДСЕТИ. ОПРОВЕРГНУТО

Сначала причиной была названа `IP_SUBNET_MASK = 32'h00FFFFFF`
(`network_stack.sv:39`) -- будто она зануляет старший байт, из-за чего соседние
адреса попадают в разные подсети и ARP уходит на несуществующий шлюз. Из этого
следовал «вывод», что адреса должны различаться **только старшим байтом** --
что справедливо было названо бредом: `dual_echo_bringup c0a80a0a ... c0a80a0b`
задавал нормальную `/24` и работал.

**Ошибка: маска применялась к адресу в ПРЯМОМ порядке байт, а внутри стека он в
СЕТЕВОМ.** `network_stack.sv:631-634` разворачивает адрес при записи:

```systemverilog
local_ip_address[7:0]   <= set_ip_addr_data[31:24];
local_ip_address[15:8]  <= set_ip_addr_data[23:16];
local_ip_address[23:16] <= set_ip_addr_data[15:8];
local_ip_address[31:24] <= set_ip_addr_data[7:0];
```

Хост пишет `0xc0a80a0a`, внутри становится `0x0a0aa8c0`. А `getDstAddr()`
(`ipv4.hpp:631`) читает `header(159,128)` **без** `reverse` -- то есть тоже
сетевой порядок. Оба операнда в одном представлении, сравнение корректно.

Пересчёт с разворотом:

| адреса | `dst & mask` | `gw & mask` | итог |
|---|---|---|---|
| 192.168.10.10 -> .11 | `0x000aa8c0` | `0x000aa8c0` | ARP напрямую, **ok** |
| 10.1.212.152 -> .153 | `0x00d4010a` | `0x00d4010a` | ARP напрямую, **ok** |

Подтверждение из самого дампа: `ch1 toe_ip_address = 98d4010a`, и
`rev(0x0a01d498) = 0x98d4010a` -- совпало. VIO читает уже развёрнутое значение,
значит разворот происходит, а маска работает как надо.

**Вывод: адреса заданы правильно, менять их бессмысленно. Маска ни при чём.**

### СЛЕДУЮЩИЙ ПРОГОН: АДРЕСА, ИСКЛЮЧАЮЩИЕ КОЛЛИЗИИ

Маска ни при чём (см. выше), но развести адреса и MAC «пошире» стоит дешево и
убирает целый класс сомнений сразу. Главное -- **новые MAC различаются в тех
байтах, которые ВИДИТ VIO**, поэтому дамп сам подтвердит, что записалось верно.

```bash
echo_bringup_dual c0a80a0a 02aa00000001 c0a80a14 02bb00000002
epd_configure c0a80a14 7001 64
epd_enable 1
epd_dump
```

`192.168.10.10` / `192.168.10.20`, MAC `02:aa:00:00:00:01` / `02:bb:00:00:00:02`.

Четыре требования, все проверены расчётом:

| требование | проверка |
|---|---|
| IP в одной подсети после разворота | `dst&mask = gw&mask = 0x000aa8c0` в обе стороны -> ARP напрямую |
| IP не равен дефолту RTL `0xD1D4010B` | иначе «незаписанный» не отличить от записанного (`network_stack.sv:626`) |
| **MAC различаются в наблюдаемых битах** | VIO покажет `0x0000aa02` против `0x0000bb02` -- РАЗНЫЕ |
| MAC локально администрируемые, не broadcast | префикс `02:` |

**Почему прежние MAC в VIO выглядели одинаково** (и это НЕ было дефектом):
`mac_addr` -- 48 бит, а probe VIO 32-битные (`network_stack.sv:1048-1064`), берутся
младшие. После разворота (`:637-642`) различающий байт `e5`/`e6` оказывается
САМЫМ СТАРШИМ и в probe не попадает. Оба канала показывали `02350a00` при реально
разных MAC. Новые адреса это лечат -- различие уходит в младшие байты.

### ЧТО ОСТАЛОСЬ НЕОБЪЯСНЁННЫМ

Главный факт по-прежнему без причины: **ch1 получает ARP-запросы (`arp_rx` растёт
на ~100/с) и не отвечает (`arp_tx` стоит на 2)**.

Проверенное и исключённое: физика (`stream_down=0`), проводка CMAC (балансы
сходятся), адреса (`toe_ip`/`arp_ip` верные в обоих каналах), маска и gateway.

`arp_server_subnet.cpp:52` отвечает при `getTargetProtoAddr() == myIpAddress`.
Значит либо в приходящем запросе target не тот, либо `myIpAddress` у ARP-сервера
отличается от `arp_ip_address`, который показывает VIO. Что именно -- **не
установлено**; проверять по RTL, чем питается порт `myIpAddress` инстанса
`arp_server_inst`, и что кладёт в target запроса `mac_ip_encode` при ARP-lookup.


### 20.08: csim TOE ПРОШЁЛ. Ядро TCP исправно, ширина ни при чём

После шести правок скрипта (все ошибки перечислены в шапке
`scripts/hls/run_toe_csim.tcl`) csim заработал и дал результат.

**Прогон 512 бит -- как в нашей сборке:**

```
INFO: Opened new session - 202
RX_SYN:      session id:0  seqNum:2675342408
TX_SYN_ACK   session id:0  ackNum:2675342409  syn:1
RX_ACK: no gap in order ... x5      <- обмен данными пошёл

```

TOE **создаёт сессию, отвечает SYN-ACK и качает данные** на нашей конфигурации
(`WINDOW_SCALE=1`, `MSS=4096`, `MAX_SESSIONS=1000`, 512 бит). Первое
положительное подтверждение: ядро TCP снимается с подозрения.

**Прогон 64 бита -- сверка.** Единственное различие в логах:

| | `(Optional) Header length` |
|---|---|
| 512 бит | 5 |
| 64 бита | 1 |

Выглядело как зацепка, но это **нормальное поведение**, посчитано точно:
`rx_engine.cpp:61` пишет `getHeaderLength() - headerWordsDropped`, а
`headerWordsDropped += WIDTH/32` (`:66`) инкрементируется ПОСЛЕ. IPv4-заголовок
160 бит собирается за 1 слово при 512 битах (отброшено 0 -> 5-0=5) и за 3 слова
при 64 битах (отброшено 4 -> 5-4=1). Значение означает «сколько 32-битных слов
заголовка ещё отбросить», и оно обязано быть разным. Совпало с логами до цифры.

**Ширина как причина -- ОТПАДАЕТ.** Handshake проходит одинаково в обеих.

### ЧТО ЗАМЕЧЕНО ПОПУТНО (не наш дефект, но знать надо)

`ipv4.hpp:91-103`, `drop_optional_header_fields` при WIDTH 256/512:

```cpp
if (WIDTH == 256 || WIDTH == 512) {
     //TODO this is a hack and only works if there are no IP options
     if (length == 5) { ... doh_state = SHIFT_FIVE; }
     // else НЕТ -- слово не читается, состояние не меняется
}
```

При IP-опциях (`IHL != 5`) на 512 битах автомат **зависает**: не читает данные и
не меняет состояние. Комментарий автора это признаёт. Наши пакеты идут без
опций, поэтому не задето, но для OUCH-гейтвея это ловушка: пакет с IP-опциями от
внешнего оборудования повесит приём.

`toe.hpp` также расходится с `toe.cpp` при `RX_DDR_BYPASS=1` -- в объявлении
`toe_core` отсутствуют `axis_data_count`/`axis_max_data_count`. Значит csim в
этой конфигурации никто не собирал.

### ГДЕ ОСТАЛОСЬ РАСХОЖДЕНИЕ

csim (без `ip_handler`, кадр подаётся прямо в `toe_core`): handshake проходит.
Плата (с `ip_handler`): SYN-ACK уходит на `0.0.0.0`.

Разница -- `ip_handler`, и по коду его путь чист: Ethernet снимается
(`rshiftWordByOctet` на `ETH_HEADER_SIZE`), IP остаётся, `detect_ipv4_protocol`
передаёт кадр как есть, в `network_stack.sv` между ними только регистровый слайс.
Формат совпадает с тем, что подаёт тестбенч.

То есть по коду расхождения нет, а на плате результат другой.

### ОГРАНИЧЕНИЯ СТЕНДА (19.08) -- учитывать при планировании

Три ограничения, каждое сужает набор допустимых проверок:

## Урок метода

Тестбенч дважды давал ложноотрицательный результат из-за длительности прогона:
`LISTEN_TIMEOUT` равен миллиону, причём в ПРОХОДАХ стадии, а не в тактах — при
II=2 это ~2 млн тактов. Прогоны на 4 000 и на 1.2 млн тактов «опровергали»
верную гипотезу.

Правило: длительность считать в проходах стадии, умножая на фактический II,
измеренный этим же тестом; константы брать из сгенерированного RTL, а не из
`.cpp`.

Второе: тестбенч на стадию отдельно НЕ ВИДИТ дефектов её окружения. Фазы 1-3
были зелёными полтора часа и вводили в заблуждение, пока `ap_continue` был
константой `1'b1` вместо `ap_sync_done`. Модель окружения надо строить по RTL
построчно, а расхождения выписывать явно — иначе «оптимистичнее железа»
превращается в «проверяет не то».

Третье, и самое дорогое: СЧИТАТЬ НАДО ПО ЖИВОЙ ШИНЕ. У probe счётчик стоял на
`m_axis_tcp_listen_port_a` — а её ведёт ЗАГЛУШКА `tie_off_tcp_listen_port`, и
она честно тикала 857 тысяч раз. Я объявил барьер снятым, глядя на активность
заглушки. Барьер действительно был снят, но подтверждала это не та цифра, а после
переключения счётчика на живую стадию стал виден второй дефект — незакрытый
таймаут в `epd_client_connect`.

Различать надо по ДРАЙВЕРУ шины, это видно в `assign` сгенерированного RTL: у
рабочей стадии слева `epd_client_connect_U0_...`, у заглушки `tie_off_...`. Так
`gen_tb_core.py` и делает теперь.
