# Почему ядра не работают на плате и что с этим делать

Состояние на 15.08.2026. Файл для нового диалога — читать целиком, он заменяет
предыдущие выводы о причинах отказа.

Предыдущий контекст (измерение задержки, врезки, тестбенчи) —
[latency_session_handoff.md](latency_session_handoff.md). Он по-прежнему верен
во всём, что касается врезок и методики; неверна только его посылка о том, что
ядра исправны и осталось лишь прошить.

## Коротко

Наши ядра (`hls_dual_echo_krnl`, `hls_echo_probe_dual_krnl`) не работают на
плате: `enable=1` читается обратно, но `listenAttempts=0`, `portState=0`, все
стадии молчат. Три битстрима подряд, детерминированно.

**Причина — схема, которую мы придумали, а не дефект в ней.** Контрольный опыт
это доказал.

## Контрольный опыт, который всё решил

`hls_recv_krnl` — апстримное ядро (`zhe`, 2020, нами не тронуто), собранное в
нашем же BD с нашим же JTAG, **работает полностью**: принимает TCP, шлёт RST на
неизвестный порт, не теряет даже первый ICMP.

Отсюда однозначно:

* **BD, `jtag_axi`, адресная карта, клок, сброс, стек, CMAC — исправны.** Они
  общие с нашими ядрами и доказаны работающим ядром в том же дизайне.
* **`jtag_axi` вместо XRT — не проблема.** Он обычный AXI-Lite мастер, и для
  `s_axilite`-ядра источник транзакций неотличим. Второе доказательство:
  `network_krnl` — тоже апстримное XRT-ядро, и по JTAG работает (пинги идут).
* **Виновата наша схема.**

Управление: `recv_bringup` / `recv_start` / `recv_status` в
[jtag_ctrl.tcl](../scripts/vivado/jtag_ctrl.tcl), смещения из сгенерированного
`xhls_recv_krnl_hw.h`.

## В чём именно ошибка схемы

Рассуждение при проектировании было такое:

1. нужна непрерывная работа → значит `ap_ctrl_none`;
2. UG1393 запрещает `s_axilite` при `ap_ctrl_none` → регистры нельзя оставить
   в ядре;
3. → нужна HDL-обёртка со своими AXI-регистрами.

Каждый шаг следует из предыдущего. **Ошибка в первом.**

Непрерывность не требует `ap_ctrl_none`. И — что важнее — её не даёт и
`auto_restart` сам по себе. У апстрима непрерывность обеспечивает **цикл внутри
стадии**:

```cpp
// communication.hpp, recvData_handshake — так делает апстрим
do {
     if (!s_axis_tcp_notification.empty()) { ... }
} while (rxByteCnt < expRxBytePerSession);
```

Ядро стартует ОДИН раз по `ap_start` и живёт внутри цикла минутами.
`auto_restart` (бит 7 в `ap_ctrl`, отсюда `0x81`) нужен лишь чтобы начать
заново, когда цикл всё-таки завершится.

А у нас стадии — функции БЕЗ цикла, с `#pragma HLS PIPELINE II=1`, отрабатывающие
за один проход. Между проходами есть рукопожатие, и в него можно потерять данные
из потоков. Это и было замечено при обсуждении: «а если 2 такта? всё
развалится?» — да, для нашей формы это реальная опасность, для апстримной её нет.

## Что известно про наши ядра достоверно

Проверено по СГЕНЕРИРОВАННОМУ RTL, не рассуждением:

| Проверка | Результат |
|---|---|
| каналы для скаляров (`p_c_U`) | **0** |
| буферы с рукопожатием (`_0_data_reg`) | **0** |
| `enableConn` до сравнения | **провод** (`epd_client_connect.v:609`) |
| `ap_start` региона | **`1'b1`** — регион free-running |
| `static` с `#pragma HLS RESET` | сбрасываются **только по `ap_rst`**, рестарт переживают |
| неблокирующая запись | есть (`grp_nbwritereq_fu_*`), стадия не висит на write |

То есть все пять дефектов HLS из старого handoff **вылечены**, и ни один из них
не является причиной. AXI-Lite тоже исправен: `enable`, `portA`, `portB`
пишутся и читаются, запись произвольного значения проходит.

**Гипотезы, которые НЕ подтвердились** (перечислены, чтобы не проверять заново):

* ранний `return` в стадии залипляет `ap_done_reg` — нет, он сбрасывается по
  `ap_continue`, и у `rx_notify` та же картина без раннего `return`;
* `ap_sync_done` (И по всем 14 стадиям) держит регион — механизм такой есть
  (`dual_echo_core.v:1337`), но не доказано, что срабатывает;
* вечный сброс из-за `resetn` без подтяжки — опровергнуто: при `ARESET=1`
  регистр `enable` не держал бы 1.

## Что делать

Привести стадии к апстримной форме — **это переписывание, а не косметика**:

```cpp
void dual_echo_listen(int enable, int listenPort, ...)
{
     while (true) {                 // <- главное, чего у нас нет
     #pragma HLS PIPELINE II=1
          if (!enable) continue;
          ...
     }
}
```

Следствия:

* `static` становятся не нужны — состояние живёт в локальных переменных внутри
  цикла, как у апстрима;
* вопрос «переживёт ли состояние рестарт» отпадает: рестарта нет;
* `s_axilite` + `ap_ctrl_hs` вместо `ap_ctrl_none`;
* **HDL-обёртка удаляется целиком** — с ней уходят `*_control_s_axi.v`, шаг
  `pack` в Makefile, адресная карта переезжает в сгенерированный `*_hw.h`;
* запуск: записать параметры → `ap_start=0x81` (как `network_start`).

Стадии, которые надо переписать:

| Ядро | Стадии |
|---|---|
| `hls_dual_echo_krnl` | `dual_echo_listen` (195), `dual_echo_rx_notify` (272), `dual_echo_rx_drain` (313) |
| `hls_echo_probe_dual_krnl` | `epd_client_connect` (170), `epd_client_traffic` (261), `epd_server_listen` (512), `epd_server_echo` (605) |

**Открытый вопрос к началу работы:** нужен ли ещё `dual_echo`. Он был ступенькой
к probe, а probe — цель. Если dual_echo больше не нужен, переписывать сразу
probe и сэкономить итерацию.

## Что при этом НЕ ломается

Врезки на `axis_net_*` (четыре больших `T`) от схемы запуска не зависят: они
живут в обёртке и работают на passthrough. Но если обёртка удаляется, врезки
надо будет куда-то перенести — вероятно, в отдельный модуль в BD между
`network_krnl` и `cmac_krnl`. Их логика (`net_frame_filter.v`, фильтр по длине +
маркер в `payload[4..9]`) проверена тестбенчами и остаётся годной.

`jtag_ctrl.tcl` придётся править: смещения `EPD_OFF_*`/`DE_OFF_*` станут другими
(их задаст HLS, а не наш `*_control_s_axi.v`). Проверка соответствия карт есть в
`test_epd_taps.tcl`, секция 12 — она поймает расхождение.

## Временное, что надо убрать

В `hls_dual_echo_krnl_wrapper.sv` и `package_hls_dual_echo_krnl.tcl` добавлен
отладочный VIO (`vio_dual_echo_dbg`, 8 проб). Он **не понадобился** — причину
нашли контрольным опытом раньше, чем дошло до сборки с ним. Если обёртка
удаляется, VIO уходит вместе с ней; если нет — удалить отдельно, он помечен как
временный.

## Что работает и трогать не надо

* сборка: `make -f Makefile.vivado xo/user_ip/pack/bd/impl` — все шаги;
* `network_krnl` и bringup стеков (`echo_bringup_dual`) — проверены на плате;
* врезки: impl прошёл, `WNS +0.0306`, битстрим собран (13.08);
* четыре набора тестов — `run_sim.sh` (76 проверок), `run_csim.tcl`,
  `test_epd_taps.tcl` (51), `test_net_frame_filter.py`. Гонять после правок;
* физика: пинги идут, ARP работает, IP защёлкивается.

## Урок метода

Контрольный опыт с заведомо рабочим чужим кодом стоил ОДНОЙ сборки и дал
больше, чем шесть часов чтения сгенерированного RTL с построением гипотез.
Делать его надо было после первой неудачной прошивки, а не после третьей.
