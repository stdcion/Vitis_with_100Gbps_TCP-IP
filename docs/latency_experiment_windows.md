# Измерение задержки TCP-стека на Alveo U200 (Windows + Vivado, JTAG)

Что измеряем: **сколько времени сообщение проводит в TCP-стеке FPGA**, без
логики гейтвея.

В прошивке два TCP-стека (по одному на порт) и одно user-ядро
`hls_echo_probe_dual_krnl`, подключённое к обоим сразу. Внутри ядра две
половины: **клиент** на порту 0 и **сервер-эхо** на порту 1. Клиент по команде
с PC отправляет пакет, тот уходит с QSFP0, идёт по кабелю на QSFP1, сервер
отвечает тем же пакетом в то же соединение, ответ возвращается на QSFP0.
Замкнутый круг.

Восемь таймстемпов на границах круга защёлкивает HDL-обёртка ядра — по **одному**
счётчику тактов на все восемь точек — и отдаёт их по JTAG сырыми. Интервалы
считает PC.

Точек восемь, потому что их две группы. Четыре маленьких `t` — на портах самого
ядра, они дают круг целиком и его три крупных части. Четыре больших `T` — врезки
на `axis_net_*`, между стеком и CMAC; они разбивают «сеть» на **стек** и
**провод**, и это то, что нужно для бюджета гейтвея: оптимизировать можно только
первое.

Критерий успеха: `epd_measure` печатает разложение круга на семь слагаемых, а
`epd_collect` — устойчивую статистику по ним (медиана близка к среднему, разброс
единицы процентов). Это и есть результат эксперимента.

Прошивается только конфигурация FPGA. **Flash не трогается** — заводская
прошивка платы остаётся на месте, после выключения питания плата вернётся к ней.

Кабель — **один, между QSFP0 и QSFP1 самой платы**. PC участвует только как
пульт по JTAG, трафик на PC не выходит вообще. Отсюда два следствия, которые
легко упустить:

- **`ping` с PC не пойдёт и не должен.** Порты соединены друг с другом, а не с
  PC. Если что-то не работает, состояние сети смотрится по счётчикам VIO
  (`vio_dump`, приложение в конце), не через `ping`.
- **Оба IP должны быть в одной подсети.** В стеке `IP_DEFAULT_GATEWAY = 0`,
  маршрутизации нет: клиент на порту 0 обращается к серверу на порту 1 напрямую
  по ARP. Подсеть /24 зашита параметром.

> **Нужна короткая версия?** [probe_runbook.md](probe_runbook.md) — вся
> последовательность от сборки до чисел одним списком, без разбора вывода.
> Этот файл — подробный: что печатает каждая команда и что делать, если не так.

## Что понадобится

| Файл                 | Куда положить           |
|----------------------|-------------------------|
| `net_bd_wrapper.bit` | `C:\net_bd_wrapper.bit` |
| `jtag_ctrl.tcl`      | `C:\jtag_ctrl.tcl`      |

Плюс:

- Vivado (любой 2022.1+, нужен только Hardware Manager),
- USB-кабель JTAG к плате (micro-USB на планке U200),
- плата запитана — U200 требует **дополнительное питание PCIe**, не только слот,
- **один** кабель QSFP0 ↔ QSFP1: DAC или пара трансиверов с патчкордом,
- две пары IP+MAC **в одной подсети /24**. В сегмент PC они попадать не обязаны:
  трафик наружу не идёт.

**Какая клетка какая:** QSFP0 — **верхняя**, QSFP1 — **нижняя** (ближе к
краевым контактам PCIe). Так в UG1289, раздел «QSFP28 Module Connector». Легко
перепутать, а симптом будет «соединение не открылось» на исправной прошивке.

Про FEC: обе стороны линка — наши CMAC с одинаковой настройкой (RS-FEC
выключен), так что здесь несовпадения быть не может. Это преимущество loopback.

## Схема эксперимента

```
                    ┌─────────────────── Alveo U200 (один ap_clk, 165 МГц) ───┐
                    │                                                          │
                    │   hls_echo_probe_dual_krnl                               │
                    │  ┌────────────────────────────────────────────────┐      │
   PC ──JTAG──► hw_axi_1 ──►│ параметры, триггер, чтение таймстемпов │   │      │
                    │  │                                                │      │
                    │  │  половина _a: КЛИЕНТ        половина _b: СЕРВЕР│      │
                    │  │       │  t1'          t2   t2'  │        t1    │      │
                    │  └───────┼───────────────┼─────┼───┼──────────────┘      │
                    │          ▼               ▲     ▼   ▲                     │
                    │     ┌─────────────────────┐  ┌─────────────────────┐     │
                    │     │ network_krnl (стек) │  │ network_krnl (стек) │     │
                    │     └─────────────────────┘  └─────────────────────┘     │
                    │          │               ▲     │   ▲                     │
                    │      T1' ▼               ▲ T2  ▼T1 ▲ T2'   врезки в      │
                    │     ┌────────────────────────────────────┐  обёртке,     │
                    │     │  passthrough + фильтр кадров       │  без регистра │
                    │     └────────────────────────────────────┘               │
                    │          │               ▲     │   ▲                     │
                    │     ┌─────────────────────┐  ┌─────────────────────┐     │
                    │     │  cmac_krnl_1  X0Y6  │  │  cmac_krnl_2  X0Y7  │     │
                    │     └─────────────────────┘  └─────────────────────┘     │
                    └──────────┼───────────────┼─────┼───┼─────────────────────┘
                            QSFP0 (верхняя)        QSFP1 (нижняя)
                               │  ▲                 │   ▲
                               └──┼─────────────────┘   │      кабель
                                  └─────────────────────┘      «сам на себя»
```

Четыре маленьких точки — это порты самого ядра, они достаются даром:

```
t1' = tx_data_a   запрос уходит в стек порта 0
t2' = rx_data_b   запрос пришёл из стека порта 1 (в эхо)
t1  = tx_data_b   ответ уходит в стек порта 1
t2  = rx_data_a   ответ пришёл из стека порта 0 (в измеритель)
```

Плюс **четыре больших `T`** — врезки на `axis_net_*`, между стеком и CMAC:

```
T1' = network_krnl_1.axis_net_tx   запрос ушёл в провод (порт 0)
T2' = cmac_krnl_2.axis_net_rx      запрос пришёл из провода (порт 1)
T1  = network_krnl_2.axis_net_tx   ответ ушёл в провод (порт 1)
T2  = cmac_krnl_1.axis_net_rx      ответ пришёл из провода (порт 0)
```

Что из них считается:

| интервал  | формула   | что внутри                                          |
|-----------|-----------|-----------------------------------------------------|
| `RTT`     | `t2 − t1'`| весь круг                                           |
| `NET_FWD` | `t2' − t1'`| стек 0 tx + CMAC + кабель + CMAC + стек 1 rx       |
| `ECHO`    | `t1 − t2'`| эхо внутри ядра: приём + заявка стеку + ответ        |
| `NET_REV` | `t2 − t1` | ответ, то же в обратную сторону                     |
| `STACK_0_TX` | `T1' − t1'` | стек порта 0: TOE + IP + merge, от заявки до провода |
| `EXT_A`   | `T2' − T1'` | CMAC0 + SerDes + кабель + SerDes + CMAC1          |
| `STACK_1_RX` | `t2' − T2'` | стек порта 1: ip_handler + TOE RX + доставка    |
| `STACK_1_TX` | `T1 − t1` | стек порта 1 на отправку ответа                   |
| `EXT_B`   | `T2 − T1` | провод в обратную сторону                           |
| `STACK_0_RX` | `t2 − T2` | стек порта 0 на приём ответа                      |

Разрешение измерения — один такт `ap_clk` = **6.061 нс** (165 МГц).

`EXT_*` — то, что **нельзя** улучшить кодом (CMAC — чёрный ящик, ~150–200 нс по
даташиту, кабель ~5 нс/м). Всё остальное — можно, и ради этого разделения
врезки и делались. Стеки раскладываются на **четыре** величины, а не на две:
`network_krnl_1` и `network_krnl_2` — физически разные экземпляры, у каждого свой
TX и RX путь, и складывать их значило бы потерять как раз ту асимметрию, которую
ищем.

Полный круг: `RTT = STACK_0_TX + EXT_A + STACK_1_RX + ECHO + STACK_1_TX + EXT_B
+ STACK_0_RX` — семь слагаемых вместо трёх.

Врезки — **чистый passthrough без регистра**: шина идёт через обёртку проводами,
и фильтр только смотрит на `tvalid & tready & tlast`. Регистр добавил бы такт
ровно в тот путь, который измеряем. Поэтому и поправка `−1` (она есть в старой
схеме-артефакте) здесь **не нужна**: она относится к варианту с регистром.

Все восемь точек штампуются из **одного** счётчика тактов, который живёт в
HDL-обёртке ядра. Само ядро время не измеряет — оно лишь считает события
(отправлено, принято эхом, отвечено, получено), а обёртка защёлкивает счётчик по
изменению этих счётчиков; для больших `T` строб идёт прямо с шины.

**На `axis_net_*` идёт весь трафик стека**, а не только наш кадр: ARP, чистые
ACK, ICMP, SYN. Поэтому врезка не берёт «первый кадр после события», а проверяет
**два независимых признака**, и они закрывают разные дырки:

- **длина** — число 512-битных слов. Служебные кадры (`ACK` 54 байта, `ARP`
  42–60, `ICMP` 42) укладываются в одно слово, наш при `msgBytes ≥ 32` занимает
  два и больше. Порог (`minWords`) пишет `epd_configure` сам вместе с
  `msgBytes`, вручную задавать не нужно.
- **маркер в payload** — константа, которую ядро кладёт в `payload[4..9]`. На
  проводе она всегда на битах 464..511 первого слова, потому что заголовки перед
  payload фиксированы (14+20+20 = 54 байта; опции TCP бывают только в SYN).

Одной длины **не хватает**: `TCP SYN` с опциями — 74 байта, то есть тоже два
слова, и от нашего кадра при `msgBytes=64` по длине не отличается. Его отсекает
маркер. И наоборот, на односоловных кадрах маркер читать нельзя — там за `tkeep`
мусор, — их отсекает длина.

Чего не отличает даже пара — **ретрансмит нашего же пакета**: та же длина, тот
же маркер. Но ретрансмит означает потерю, её видно по `timeoutCount`, и такой
замер и так уходит в `discarded`.

Разбор целиком — в [latency_net_probe_design.md](latency_net_probe_design.md).

Это существенно, а не деталь реализации: `NET_FWD` и `NET_REV` вычитают точки
**разных половин** ядра. На двух раздельных счётчиках любое их расхождение
завысило бы одно ровно настолько, насколько занизило другое, — не задев ни `RTT`,
ни `ECHO`, ни проверку баланса, то есть незаметно для всех проверок на хосте.

**Если частота менялась — поправить в четырёх местах**, иначе перевод тактов в
наносекунды будет врать молча: `DEV_FREQ_MHZ` в `devices/<board>/device.tcl.in`,
`EPD_CLK_NS` в `jtag_ctrl.tcl`, `create_clock` в `src/hls/run_csim.tcl` и число
выше в этом абзаце.

## 1. Подключиться к плате

Vivado → **Open Hardware Manager** (Flow Navigator слева, либо
`Flow → Open Hardware Manager`), дальше **Open Target → Auto Connect**.

В панели Hardware появится:

```
localhost (1)
  xilinx_tcf/Xilinx/<серийник>
    xcu200_0 (0)
```

Нет устройства — проверить USB-кабель и питание платы.

## 2. Загрузить битстрим

Правый клик по `xcu200_0` → **Program Device**.

- **Bitstream file**: `C:\net_bd_wrapper.bit`
- **Debug probes file**: оставить пустым

**Program**, занимает ~30–60 секунд.

После загрузки под `xcu200_0` появятся отладочные ядра, среди них `hw_axi_1`
(JTAG-to-AXI, через него всё управление), `hw_ila_*`, `hw_vio_*` и `MIG_1`.

**`hw_axi_1` обязателен** — без него скрипт управления работать не будет.

## 3. Проверить DDR4

Двойной клик по `MIG_1` → таблица стадий калибровки, все должны быть `PASS`.

Или в Tcl Console:

```tcl
get_property STATUS.CAL_STATUS [get_hw_migs]
```

Не прошла калибровка — дальше идти бессмысленно: TCP-стек держит таблицы
сессий в DDR4. Оба порта используют одну память, встанут сразу оба.

## 4. Загрузить скрипт управления

В Tcl Console (внизу окна Vivado):

```tcl
source C:/jtag_ctrl.tcl
```

Слеши **прямые**, даже на Windows — Tcl трактует `\` как escape-символ.

Скрипт только объявляет процедуры, ничего не выполняет. Молчание — нормально.

## 5. Поднять оба стека

Ядро измерения не задаёт IP/MAC — это свойство стека, их пишет отдельная
процедура.

```tcl
echo_bringup_dual 0a01d498 000a35029de5 0a01d499 000a35029de6
```

Аргументы — **две** пары IP+MAC в hex, без `0x` и без разделителей: сначала
порт 1 (QSFP0), затем порт 2 (QSFP1).

| Что | Пример                               | Как перевести                                   |
|-----|--------------------------------------|-------------------------------------------------|
| IP  | `10.1.212.152` → `0a01d498`          | каждый октет в hex: 10=0a, 1=01, 212=d4, 152=98 |
| MAC | `00:0a:35:02:9d:e5` → `000a35029de5` | убрать двоеточия                                |

Ограничения на адреса:

- **Оба IP в одной подсети /24** — маршрутизации в стеке нет.
- **Последние октеты IP обязаны различаться.** ARP-таблица стека —
  `arpTable[256]`, индексируемая одним октетом, и внутри стека адреса лежат
  LSB-first, то есть индексом служит **последний** октет. У пары `.152` / `.153`
  индексы 152 и 153, коллизии нет. У пары `10.1.1.152` / `10.1.2.152` вторая
  запись затрёт первую, и соединение не откроется.
- MAC любые уникальные; локально администрируемые (`02:00:00:00:00:01`,
  `02:00:00:00:00:02`) гарантированно ни с чем не столкнутся.

Что должно напечататься на каждый канал:

```
=== bringup channel 1 (echo) ===
network_krnl: ip=0x0a01d498 mac=0x000a35029de5
  read back:  ip=0x0a01d498 mac=0x000a35029de5
  write confirmed
network_krnl[1]: axi00_ptr0=0x00000000 axi01_ptr0=0x40000000
network_krnl[1]: ap_ctrl=0x81 (ap_start=1 ap_done=0)
=== done, channel 1 is listening on the port hardcoded in hls_echo_krnl.cpp ===
```

Ждём **`write confirmed` дважды** — скрипт читает регистры обратно. Нет
строки — JTAG не достучался до платы, всё дальнейшее бессмысленно.

Упоминание `hls_echo_krnl.cpp` в выводе — косметика, процедура общая для
echo-ядер.

## 6. Померить цену JTAG-транзакции

```tcl
epd_calibrate
```

```
JTAG: 100 чтений за <N> мс = <X> мс на транзакцию
      один замер (~10 транзакций) ≈ <Y> мс
```

Это делается **до** сбора статистики, потому что от результата зависит, сколько
замеров имеет смысл заказывать. Правдоподобный диапазон — от полумиллисекунды
до десятков миллисекунд; заранее неизвестно, поэтому и меряем.

На точность самого эксперимента цена транзакции не влияет: таймстемпы ставит
железо, JTAG только читает готовые числа. Влияет только на то, сколько времени
займёт `epd_collect`.

## 7. Настроить измеритель

```tcl
epd_configure 0a01d499 7001 64
```

Аргументы: **IP сервера** (порт 1, hex без `0x`), **порт** и **размер
сообщения в байтах**.

- IP сервера — это IP **второго** порта, тот же, что был вторым аргументом
  `echo_bringup_dual`. Клиент на порту 0 подключается к серверу на порту 1.
- Порт слушания скрипт выставляет равным порту подключения, отдельно задавать
  не нужно.
- `msgBytes` округляется вверх до кратного 64 (ширина шины). Ноль трактуется
  как 64, потолок — **4096** байт (`EPD_MAX_WORDS = 64` слов по 64 байта),
  больше молча обрежется.

```
epd[1]: server=0x0a01d499:7001 msg=64 bytes
  write confirmed
```

**Нет `write confirmed`** — ядро не отвечает по JTAG на этих регистрах.
Скорее всего загружен не тот `.bit` (в плате осталась прошивка от другого
эксперимента) — перепрошить и повторить с шага 4. Если после перепрошивки то же
самое, сообщите нам вывод `epd_configure` целиком.

## 8. Разрешить работу

```tcl
epd_enable 1
```

`enable` **всегда последним**, после `epd_configure`. До него ядро не трогает
порты стека — иначе клиент попытался бы открыть соединение по мусорному адресу
из ещё не записанных регистров.

## 9. Проверить, что соединение открылось

```tcl
epd_status
```

```
epd[1]: connAttempts=1 sent=0 echoRx=0 echoes=0 recv=0 timeouts=0 ready=0
epd[1]: server listen: attempts=1 state=2(OPEN)
```

Что должно быть на этом этапе: **`connAttempts` ≥ 1** и **`state=2(OPEN)`**,
остальное нули — пакеты ещё не посылались, триггер не дёрнут.

`epd_status` сама печатает диагностику, если цепочка где-то оборвалась. Порядок
проверок идёт по тракту, от серверного listen к обратному пути:

| симптом | что печатает | смысл |
|---|---|---|
| `state=0` | `the server has not requested a listen port` | `enable` не записался |
| `state=1` | `the stack has not answered` | стек не ответил на запрос listen; `epd_enable` до `echo_bringup_dual`? |
| `connAttempts=0` | `the client never tried to open a connection` | `enable` не записался |
| `sent=0`, attempts > 3 | `connection did not open` | адресация: одна /24, разные последние октеты — см. «Если не работает» |
| `sent>0`, `echoRx=0` | `the request never reached port 1` | линк, кабель или размещение CMAC |
| `echoRx>0`, `echoes=0` | `the echo RECEIVED the request but never sent a reply` | **внутри ядра**, не в сети: эхо ждёт `tx_status` от стека 1 |
| `echoes>0`, `recv=0` | `the echo replied but the reply never came back` | обратный путь |

**`echoRx` отделяет «запрос не дошёл» от «дошёл, но ответа не было».** Без него
`echoes=0` означало сразу оба случая, а это разные диагнозы: первый — сеть,
второй — логика ядра.

Растущий `connAttempts` при нулевом `sent` — соединение не открывается, клиент
повторяет. Разбор по пунктам — в «Если не работает».

## 9а. Проверить врезки на `axis_net_*`

```tcl
epd_net_status
```

```
epd[1]: net taps: minWords=2
epd[1]:   channel A (QSFP0): passed=14 dropped=27
epd[1]:   channel B (QSFP1): passed=14 dropped=27
```

Это **не измерение**, а проверка живости — но сделать её надо ДО первого замера,
иначе «нули в таймстемпах `T`» будет не отличить от «врезка подключена не туда».
Смысл в паре чисел, не в каждом по отдельности:

| `passed` | `dropped` | Что это значит |
|---|---|---|
| растёт | растёт | **норма**: наши кадры проходят, ARP/ACK отсеиваются |
| `0` | растёт | фильтр режет **всё**, включая наш кадр — `minWords` завышен. Перезапустить `epd_configure` |
| `0` | `0` | врезка **мертва**: битстрим без врезок, либо `config_sp` не развернул `axis_net_*` через обёртку |

`dropped` больше `passed` — это нормально и ожидаемо: на каждый наш кадр
приходится ARP и минимум один чистый ACK, и все они одноcловные.

Если оба канала показывают `0/0`, а четыре маленьких `t` при этом работают —
загружен битстрим, собранный до врезок. Измерение по четырём точкам пойдёт как
раньше, разложения на семь слагаемых не будет.

## 10. Один замер

```tcl
epd_measure
```

```
  raw t: t1'=<N> t2'=<N> t1=<N> t2=<N>
  raw T: T1'=<N> T2'=<N> T1=<N> T2=<N>
  RTT        <N> cycles     <N> ns
  NET_FWD    <N>            <N>
  ECHO       <N>            <N>
  NET_REV    <N>            <N>

  --- decomposition, seven terms ---
  STACK_0_TX <N> cycles     <N> ns   request into the wire (port 0)
  EXT_A      <N>            <N>      CMAC+cable+CMAC, forward
  STACK_1_RX <N>            <N>      wire to application (port 1)
  ECHO       <N>            <N>      inside the kernel
  STACK_1_TX <N>            <N>      reply into the wire (port 1)
  EXT_B      <N>            <N>      CMAC+cable+CMAC, reverse
  STACK_0_RX <N>            <N>      wire to measurer (port 0)

  residual fwd +<N> cycles, rev +<N>
```

Первые две строки — **сырые счётчики**, как их защёлкнула обёртка; всё ниже PC
считает из них. Если `t2` меньше `t1'`, счётчик обернулся за время замера — это
нормально, вычитание идёт по модулю 2^32, и скрипт про это пишет сам.

Если вместо разложения печатается `(no axis_net_* taps in this bitstream)` —
загружен битстрим, собранный до врезок. Четыре первых числа при этом верны.

**Это результат эксперимента.** Что смотреть:

- **`NET_FWD` ≈ `NET_REV`.** Тракт симметричный, сильная разница подозрительна.
- **`ECHO` — десятки тактов.** Это путь внутри ядра: эхо принимает сообщение,
  запрашивает у стека место под ответ и ждёт подтверждения. Сотни тактов
  означают, что оно ждёт чего-то ещё, и тогда `NET_*` тоже под вопросом.
- **`EXT_A`, `EXT_B` — единицы-десятки тактов.** Это сериализация 64 байт на
  100G (~5 нс) плюс SerDes туда-обратно (десятки нс). **Сотни тактов означают,
  что врезка ловит не тот кадр** — тогда `epd_net_status` и раздел «Чужой
  трафик на шине» в проекте врезок.
- **`residual` — такт-два.** Это единственная строка здесь, которая **не**
  тождество, и поэтому единственная, которая несёт информацию. Точки `t`
  штампуются по `ap_vld` зарегистрированного выхода HLS, точки `T` — прямо с
  шины; пути разные, и `t` может отставать от `T` на такт. Малый постоянный
  residual — это и есть та поправка, которую потом сложат в четыре `STACK_*`.
  **Десятки тактов означают, что фильтр защёлкнулся на чужом кадре.**
- **Повторяемость.** Один замер ничего не доказывает — смотреть надо
  `epd_collect` (шаг 11).

Чего **не** стоит делать — проверять «баланс» `NET_FWD + ECHO + NET_REV = RTT`
как признак хорошего замера. Это алгебраическое тождество: сумма сворачивается
в `t2 − t1'` при любых четырёх числах. Разойтись она может только если регистр
прочитан в момент обновления, и тогда скрипт печатает `*** TORN READ`.

Чего эта проверка **не** увидит, хотя выглядит будто должна:

- **смешение таймстемпов разных пакетов** — от него защищает режим одного
  пакета по триггеру, а не арифметика;
- **сдвиг шкал между половинами** — он бы завысил `NET_FWD` и занизил `NET_REV`
  на одну и ту же величину, и сумма сошлась бы. Поэтому шкала сделана
  физически одной (см. «Схема эксперимента»), а не проверяется постфактум.

То есть `ok` в `epd_raw` означает «арифметика непротиворечива», а не «числа
правдоподобны». Судить надо по разбросу и по симметрии `NET_FWD` ≈ `NET_REV`.

```
epd: sample failed (no sampleReady within the timeout)
```

Круг не замкнулся за 500 мс. Скрипт сам вызовет `epd_status` — смотреть по
таблице шага 9. У ядра свой таймаут ожидания ответа (`EPD_RX_TIMEOUT`, ~6 мс),
после него потерянный пакет засчитывается в `таймаутов` и клиент идёт дальше,
так что тест не зависает.


```
                    from (EXT_A+EXT_B)/4, cable ignored (<1 cycle)

                    STACK_1_RX + STACK_1_TX + 2*CMAC_ONE, logic = 0

```

(числа для примера — какими они окажутся, и есть вопрос эксперимента)

Две сводные величины считаются бесплатно из тех же замеров:

- **`CMAC_ONE = (EXT_A + EXT_B) / 4`** — задержка одной стороны одного CMAC.
  Отдельная калибровочная сборка не нужна: внешние дельты дают её из того же
  замера. Кабель (~5 нс/м, меньше такта) отброшен как поправка второго порядка.
- **`E2E floor`** — бюджет одного прохода гейтвея от кабеля до кабеля: приём на
  одном порту, обработка, передача на другом. **Это и есть то число, ради
  которого всё измеряется** — но именно «пол»: логика гейтвея не написана, и
  вместо неё в круге стоит почти нулевой `ECHO`.

Плюс две проверки симметрии, которые скрипт печатает только при расхождении
больше 1.5×:

- **`EXT_A` против `EXT_B`** — они и не обязаны совпадать: порт 0 на `QPLL0`,
  порт 1 на `QPLL1`, разные GT-квады.
- **`STACK_0_RX` против `STACK_1_RX`** — а вот это один и тот же `network_krnl` в
  двух экземплярах, и расхождение здесь означает внешнее влияние: конкуренцию за
  DDR4 или размещение по SLR. Смотреть `make -f Makefile.vivado report`.

**`warm-up: 3`** — первые три замера отброшены до начала подсчёта, и это не
подгонка. Пакеты сразу после `epd_enable` идут по тракту вместе с установкой
соединения: SYN/SYN-ACK клиента, первый обмен ARP (стеки узнают MAC друг друга),
и самый первый проход через TOE, когда его таблицы сессий в DDR4 ещё холодные. Их
таймстемпы законно отличаются от установившегося режима, и в статистике они дали
бы завышенный `max` и предупреждение про выброс на ровном месте.

Трёх достаточно: установочного трафика — считанные кадры, а не разгон. Поднимать
`EPD_WARMUP` без нужды не стоит — так прячется не шум, а реальное поведение.
Основание для увеличения — только если в `epd_raw` видно, что переходный процесс
длиннее.

**Главное — медиана против среднего.** Разошлись сильно, или `max` заметно
выше медианы — в выборке выброс, и среднему верить нельзя. Скрипт сам
предупредит, если `max` больше трёх медиан:

```
  *** OUTLIER: max RTT (5000) is more than 3x the median (665).
```

Тогда смотреть `epd_raw` (ниже) и искать, какой замер испортил статистику.

Таймауты и разорванные чтения попадают в `discarded` и в статистику не идут.
Единичные отбросы терпимы; **половина отброшенных — результат недействителен**,
разбираться до того, как записывать числа.

Десятков замеров достаточно: мы измеряем порядок величины и разброс. Тысячи
нужны для хвоста распределения, а это отдельная задача — замер под нагрузкой,
там понадобится поток и `seq_id` в payload.

### Сырые данные для внешнего анализа

```tcl
epd_raw 20
```

Печатает CSV: по строке на замер, сырые счётчики **и** посчитанные из них
интервалы.

Столбцов 21: номер замера, восемь сырых стемпов, четыре классических интервала,
шесть из врезок, `ns_rtt` и `status`. Строки в примере укорочены до значимого —
в файле они полной ширины.

```
sample,t1p,t2p,t1,t2,T1p,T2p,T1,T2,rtt,net_fwd,echo,net_rev,stack0_tx,ext_a,stack1_rx,stack1_tx,ext_b,stack0_rx,ns_rtt,status
0,504,807,869,1170,645,666,1006,1028,666,303,62,301,141,21,141,137,22,142,4036.6,ok
2,,,,,,,,,,,,,,,,,,,,TIMEOUT
4,12490,12800,12862,18990,...,6500,310,62,6128,...,4036.6,ok
5,4294967100,12,74,371,...,567,208,62,297,...,3436.6,ok
```

**Колонки.** `p` в имени — это штрих (prime); апостроф в CSV сломал бы парсинг в
Excel и pandas, поэтому `t1'` записан как `t1p`.

| В CSV | В схеме | Что защёлкнуто |
|---|---|---|
| `t1p` | `t1'` | `tx_data_a` — клиент отдал последнее слово запроса |
| `t2p` | `t2'` | `rx_data_b` — эхо приняло последнее слово запроса |
| `t1`  | `t1`  | `tx_data_b` — эхо отдало последнее слово ответа |
| `t2`  | `t2`  | `rx_data_a` — клиент принял последнее слово ответа |
| `T1p` | `T1'` | `network_krnl_1.axis_net_tx` — запрос ушёл в провод |
| `T2p` | `T2'` | `cmac_krnl_2.axis_net_rx` — запрос пришёл из провода |
| `T1`  | `T1`  | `network_krnl_2.axis_net_tx` — ответ ушёл в провод |
| `T2`  | `T2`  | `cmac_krnl_1.axis_net_rx` — ответ пришёл из провода |

Штрих у первых двух — это первая половина круга (запрос), без штриха — вторая
(ответ). Порядок колонок **хронологический**, по ходу пакета, поэтому значения в
строке должны возрастать; исключение — переполнение счётчика (см. ниже).

Хронология полного круга, по которой сверять строку:
`t1' → T1' → T2' → t2' → t1 → T1 → T2 → t2`.

Шесть столбцов врезок **пусты**, если загружен битстрим без них. Это намеренно:
из нулевых `T` можно было бы посчитать интервалы, и получились бы огромные
правдоподобные числа (`0 − t1'` по модулю 2^32), а пустая клетка видна сразу.

Имена регистров в адресной карте — по смыслу, а не по обозначению:
`tsRequest`=`t1'`, `tsEchoIn`=`t2'`, `tsEchoOut`=`t1`, `tsReply`=`t2`,
`tsNetTxA`=`T1'`, `tsNetRxB`=`T2'`, `tsNetTxB`=`T1`, `tsNetRxA`=`T2`
(таблица в шапке `src/hdl/probe_control_s_axi.v`).

**Любую строку можно пересчитать вручную** — в этом и смысл сырого дампа:

```
rtt     = t2  − t1p        666 = 1170 − 504
net_fwd = t2p − t1p        303 =  807 − 504
echo    = t1  − t2p         62 =  869 − 807
net_rev = t2  − t1         301 = 1170 − 869
ns_rtt  = rtt × EPD_CLK_NS      666 × 6.061 = 4036.6
```

**Три особых случая, все три есть в примере выше:**

* **строка 2, `TIMEOUT`** — круг не замкнулся за 500 мс, `sampleReady` не встал,
  читать было нечего. Попадает в `discarded` у `epd_collect`.
* **строка 4, выброс с меткой `ok`** — `net_rev=6128` против обычных ~296, `rtt` в
  десять раз больше медианы. Сумма при этом сходится идеально
  (`310+62+6128 = 6500`), потому что это тождество. `epd_collect` такую строку
  **не отбросит**, она пройдёт в статистику и испортит `mean`; поймает только
  предупреждение `*** OUTLIER`. Зато по сырым числам сразу видно, что задержка на
  ОБРАТНОМ пути (`net_fwd` в норме) — то есть смотреть надо стек порта 0 на приём,
  а не весь тракт.
* **строка 5, переполнение** — `t1p=4294967100`, `t2p=12`: 32-битный счётчик
  обернулся посреди замера (на 165 МГц это раз в 26 с). Вычитание идёт по модулю
  2^32, поэтому интервалы посчитаны корректно; на результат переполнение не
  влияет.

Неудачные замеры не выбрасываются, а помечаются в `status`: `TIMEOUT` — круг не
замкнулся, `TORN` — регистр прочитан в момент обновления. **`ok` не означает
«правдоподобно»** — выброс с согласованной суммой тоже будет `ok`, судить надо
по разбросу.

**`epd_raw` не делает разогрева**, в отличие от `epd_collect`: печатает всё
подряд, включая первые замеры после `epd_enable`. Это осознанно — сырой дамп
должен показывать то, что агрегат отбросил. Поэтому первые 2–3 строки в файле
могут законно отличаться: там установка соединения, SYN/ARP и холодные таблицы
TOE.

Сохранить в файл:

```tcl
set fh [open C:/epd_raw.csv w]; puts $fh [epd_raw 50]; close $fh
```

## 12. Свип по размеру сообщения

**Пересборка не нужна** — для этого параметры и вынесены в регистры управления
(их держит HDL-обёртка ядра, `src/hdl/probe_control_s_axi.v`):

```tcl
epd_configure 0a01d499 7001 128
epd_collect 20
epd_configure 0a01d499 7001 256
epd_collect 20
epd_configure 0a01d499 7001 1500
epd_collect 20
```

`epd_enable` повторно дёргать не нужно, соединение уже открыто.

Разогрев `epd_collect` делает сам на каждом вызове, поэтому смена `msgBytes`
между сериями не портит статистику: первые замеры нового размера отбрасываются
так же, как после `epd_enable`. Это существенно — при первом пакете нового
размера TOE заново решает, как его сегментировать.

Что ожидается: `RTT` растёт с размером примерно линейно (сериализация на 100G),
а точка пересечения с нулём — это и есть постоянная составляющая, тот самый
«пол» стека. Именно она нужна для бюджета гейтвея.

Потолок — 4096 байт (шаг 7). Выше него числа перестанут расти, потому что ядро
обрежет сообщение, а не потому что тракт стал быстрее.

## Если не работает

Первое, что стоит сделать при любом отказе, — `vio_dump` (см. «Счётчики стеков»
в конце документа). Он показывает, дошло ли дело до сети вообще.

**`epd_configure` не подтверждает запись.** Ядро не отвечает по JTAG. Проверить,
что прошит именно присланный `C:\net_bd_wrapper.bit` и что `hw_axi_1` есть в
дереве (шаг 2), затем повторить с шага 4.

**Соединение не открывается** (`попыток соединения` растёт, `отправлено` = 0).
Порядок разбора по `vio_dump`:

1. **IP и MAC (пробы 0–4) нулевые или не те** — bringup не сработал, повторить
   шаг 5.
2. **Все счётчики пакетов по нулям на обоих стеках** — линк не встал физически.
   Кабель не вставлен, вставлен в одну клетку, или трансивер неисправен. Обе
   стороны здесь — наши CMAC с одинаковым FEC, так что несовпадение настроек
   исключено.
3. **`arp_tx` растёт, `arp_rx` = 0** — запросы уходят, ответов нет. Кабель в
   одной клетке, а не в двух.
4. **ARP в обе стороны идёт, `tcp_*` по нулям** — линк и ARP живые, дело в
   адресах: оба IP в одной подсети /24, последние октеты различаются (шаг 5).
   Это самая вероятная причина при живой сети.
5. **`stream_down` (проба 17) ненулевой** — срывы шины, числам верить нельзя;
   сообщите нам.

**`ECHO` в сотни тактов.** Эхо ждёт чего-то, чего мы не учли. Числа `NET_*` в
этом случае тоже недоверенные — сообщите нам вывод `epd_measure` и `epd_status`.

**`*** OUTLIER` в сводке `epd_collect`.** В выборке замер, выбивающийся от
медианы больше чем втрое. Смотреть `epd_raw` — какой это замер и что у него в
сырых счётчиках. Единичный выброс на десятках замеров бывает; если выбросов
много, среднее считать нельзя, сообщите нам CSV.

**`TORN` в колонке `status` у `epd_raw`.** Регистр прочитан в момент
обновления — арифметически такой набор невозможен. Единичный случай можно
отбросить, регулярные — сообщите нам, это проблема транспорта JTAG.

**После выключения платы всё пропало.** Так и задумано, конфигурация FPGA
волатильная. Повторить шаги 2–8.

```tcl
foreach sz {64 128 256 512 1024 1500} {
     epd_configure 0a01d499 7001 $sz
     set fh [open C:/epd_raw_$sz.csv w]
     puts $fh [epd_raw 20]
     close $fh
     puts "--- $sz bytes done ---"
}
```

## Что сообщить о результате

- вывод `epd_calibrate` — цена JTAG-транзакции;
- вывод `epd_status` после `epd_enable 1`;
- вывод `epd_net_status` — живы ли врезки на `axis_net_*` и что показывает пара
  `passed`/`dropped`;
- вывод `epd_measure` — один замер целиком, включая строки `raw t:`/`raw T:` и
  строку `residual`;
- сводки `epd_collect 20` для каждого размера сообщения из свипа, вместе со
  строкой `N samples out of 20 (discarded: M)`;
- **файлы `epd_raw_*.csv`** — сырые счётчики, по ним статистику можно
  пересчитать и проверить независимо;
- если что-то не поднялось — вывод `echo_bringup_dual` целиком плюс `vio_dump`.

## Приложение: счётчики стеков (`vio_dump`)

Справочник к процедуре из «Если не работает». В штатном прогоне не нужна —
вызывать, когда что-то не работает.

```tcl
vio_dump
```

Процедура уже в `jtag_ctrl.tcl`, отдельно вставлять в консоль ничего не нужно.
Печатает все пробы обоих VIO с расшифрованными именами:

```
--- .../network_krnl_1/inst/vio_network ---
  ip_toe      (probe_in0)      0a01d498
  ...
  arp_rx      (probe_in11)     3
  arp_tx      (probe_in12)     3
  stream_down (probe_in17)     0
```

Что это за пробы: `vio_network` из
`kernel/network_krnl/src/hdl/network_stack.sv`, 19 входов на каждый стек.

| проба | имя | что |
|---|---|---|
| 0–4 | `ip_toe` `ip_iph` `mac_mie` `mac_arp` `ip_arp` | IP и MAC, как их видит стек |
| 5–8 | `rx_words` `rx_pkts` `tx_words` `tx_pkts` | слова и пакеты, всего |
| 9–10 | `tcp_rx` `tcp_tx` | пакеты TCP |
| 11–12 | `arp_rx` `arp_tx` | пакеты ARP |
| 13–14 | `udp_rx` `udp_tx` | пакеты UDP |
| 15–16 | `icmp_rx` `icmp_tx` | пакеты ICMP |
| 17 | `stream_down` | срывы шины |
| 18 | `mac_addr` | MAC интерфейса |

Две тонкости, из-за которых показания легко истолковать неверно:

- **`refresh_hw_vio` обязателен.** Без него Vivado отдаёт значения, считанные при
  загрузке битстрима, то есть нули — выглядит как «стек мёртв». Он внутри
  `vio_dump`, отдельно вызывать не нужно; но если читать пробы руками через GUI,
  про обновление придётся помнить.
- **Какой VIO какому порту.** Смотреть путь в шапке `--- ... ---`, там
  `network_krnl_1` или `network_krnl_2`. По номерам `hw_vio_1` / `hw_vio_2`
  судить нельзя, они не гарантированно соответствуют портам.

### Чего в VIO нет

**`stat_rx_aligned` и `stat_rx_status`** — на VIO не выведены. Они на **ILA** в
`cmac_krnl` (`inst_ila_0`, `probe0` = `stat_rx_aligned_1d`), а ILA читается не
значением, а запуском на триггер: двойной клик по `hw_ila_1` → **Run Trigger** →
смотреть волну `probe0`. Для вопроса «встал линк или нет» это лишняя работа:
счётчики ARP отвечают на него сразу.
