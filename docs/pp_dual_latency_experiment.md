# Эксперимент 2: разбивка задержки по участкам

**Что измеряем: сколько добавляет стек TOE, а сколько наше ядро.**

Полный RTT `ppclient` показывал и раньше, но в одном числе. Здесь впервые видно
раздельно: приём стеком, работа ядра, передача стеком.

**Предусловие: эксперимент 1 прошёл** — эхо возвращается. Если нет, измерять
нечего, см. `pp_dual_echo_experiment.md`.

## Четыре точки на пути пакета

```
   QSFP0                U200
     │
  ┌──▼───┐
  │CMAC0 │  ~150-200 нс, вне измерения
  └──┬───┘
     │  axis_net_rx  ──► T2   кадр пришёл на край стека
  ┌──▼──────────────┐
  │ network_krnl_1  │  ← STACK_RX = t2 - T2
  │   (TOE, DDR)    │
  └──┬──────────────┘
     │  rx_data.tlast ──► t2  payload дошёл до ядра
  ┌──▼──────┐
  │ pp_echo │            ← KERNEL = t1 - t2
  └──┬──────┘
     │  tx_data.tlast ──► t1  ядро отдало payload
  ┌──▼──────────────┐
  │ network_krnl_1  │  ← STACK_TX = T1 - t1
  └──┬──────────────┘
     │  axis_net_tx  ──► T1   кадр ушёл на край стека
  ┌──▼───┐
  │CMAC0 │
  └──────┘
```

Метки снимаются **одним счётчиком тактов** в HDL-обёртке — иначе значения
разных стадий не сравнить (при разном II они расходятся невидимо).

CMAC и кабель за врезкой, со стороны провода. Для нашей задачи это и не нужно:
интересна задержка, которой мы управляем.

## Как железо узнаёт наш пакет

На `axis_net` идёт **весь** трафик стека: ARP, чистые ACK, ICMP, SYN. Без
фильтра врезка защёлкнулась бы на первом попавшемся кадре.

Фильтр (`net_frame_filter.v`) отличает наш кадр по двум признакам через И:

| признак | что отсекает |
|---|---|
| длина ≥ 2 слов по 512 бит | ACK (54 б), ARP (42-60), ICMP — все в одно слово |
| маркер `D2 B7 E1 96 3C 5A` в payload[4..9] | SYN с опциями — 74 б, тоже два слова |

**Маркер пишет `ppclient`**, поэтому измерения работают только с ним. `telnet`
или `ncat` дадут эхо, но фильтр их не узнает и FIFO останется пустым.

Смещение фиксировано: заголовки Ethernet 14 + IP 20 + TCP 20 = 54 байта
неизменно (опции стек добавляет только в SYN), значит `payload[4..9]` попадает
на байты кадра 58..63 при любом размере сообщения.

## FIFO: почему пачкой, а не по одному

Четыре сырые метки на измерение, 128 измерений в FIFO. Читаются после прогона.

Так, а не «пакет — чтение — пакет», потому что чтение по JTAG занимает
миллисекунды: ядро простаивало бы между пакетами, кэши TOE остывали, и
измерялись бы единичные пакеты в идеальных условиях, а не задержка под
нагрузкой.

При переполнении **новые записи отбрасываются, старые целы**, и потеря
считается в `fifoOverflow`. Кольцевое затирание дало бы при чтении смесь начала
и конца прогона, неразличимую по номерам.

## Порядок

Шаги 1–2 те же, что в эксперименте 1: прошить, `pp_dual_bringup`, убедиться что
`portState = 2`.

### 3. Проверить, что фильтр узнаёт кадры

```tcl
pp_taps_status
```

**Запускать до чтения FIFO.** Отвечает на вопрос, который дамп не может: видит
ли железо наши пакеты вообще.

| что видно | вывод |
|---|---|
| `filter RX passed` растёт, `TX passed` растёт | узнаёт в обе стороны — можно мерить |
| `RX passed 0`, `dropped` растёт | **ничего не проходит**: нет маркера (запускали не `ppclient`?), завышен `minWords`, или врезка не туда подключена |
| `RX` растёт, `TX passed 0` | запросы узнаны, ответы нет — ядро не отвечает либо ответ потерял маркер |
| оба 0 | до врезки трафик не дошёл: кабель, стек, `config_sp` |

Пустой FIFO бывает по четырём причинам, и эти счётчики их различают. Дамп — нет.

### 4. Очистить FIFO перед прогоном

```tcl
pp_clear
```

Чистит данные, но **не** счётчик потерь: потери прошлого прогона должны
остаться видны.

### 5. Прогон с компьютера

```
ppclient.exe -host 192.168.10.10 -port 7001 -bytes 64 -count 100 -csv rtt.csv
```

Сто пакетов — FIFO вмещает 128, переполнения не будет.

### 6. Снять измерения

```tcl
pp_measure
```

Или в файл для анализа потом:

```tcl
pp_save C:/pp_raw.csv
```

Путь **с прямыми слешами**: Tcl трактует обратный как экранирование, и
`C:\pp_raw.csv` молча станет `C:pp_raw.csv` в текущем каталоге.

## Что покажет `pp_measure`

```
=== gateway latency, 100 measurements ===
  stack RX  T2->t2   min   ...  med   ...  max   ... cycles   (med ... us)
  kernel    t2->t1   min   ...
  stack TX  t1->T1   min   ...
  TOTAL     T2->T1   min   ...
```

`min` — то, что сравнивать с бюджетом: это путь без очередей. `med` несёт
queueing, `max` — выбросы.

## Предсказания, записанные ДО прогона

Из оценки бюджета (`toe-latency-budget-estimate`), такт 6.061 нс:

| участок | ожидание, тактов | уверенность |
|---|---|---|
| `stack RX` (T2→t2) | 50–80 | средняя (`RX_DDR_BYPASS=1`, DDR не касается) |
| `kernel` (t2→t1) | 25–65 | средняя (автомат 6 состояний, `STATUS` ждёт круг через TOE) |
| `stack TX` (t1→T1) | 100–150 | низкая (чужой TOE плюс DDR4, флагом не отключается) |
| **TOTAL** | **175–295** | ≈ 1.1–1.8 мкс |

**Три проверки, которые либо подтвердят модель, либо покажут ошибку:**

1. **`stack TX` примерно вдвое больше `stack RX`** — следствие асимметрии DDR:
   приём в обход, передача через TX-буфер. Наоборот → я неверно читаю стек.
2. **`kernel` не меньше 25 тактов.** Один такт невозможен: TOE требует
   `tx_meta` до отправки данных, отсюда store-and-forward и `payload[]`.
   Меньше — значит метки склеены не от того пакета.
3. **`kernel` линеен по размеру**: между 64 и 1024 байтами разность ровно 15
   тактов (по одному на 64-байтное слово). Нет → `STATUS` не константа, ждёт
   разное время.

Проверка 3 требует второго прогона с `-bytes 1024`.

## Колонка `ok` в CSV — три состояния

| | значение |
|---|---|
| `ok` | метки согласованы, сумма интервалов равна полному |
| `TORN` | сумма не сходится (арифметически невозможно, но проверяем) |
| `HUGE` | полный интервал > 100000 тактов = 606 мкс |

`HUGE` при бюджете 1.8 мкс означает не «медленно», а **метки от разных
пакетов**. `pp_measure` такие строки исключает из статистики **и считает** в
выводе: молча выбросить значило бы спрятать именно те случаи, на которые стоит
смотреть.

## Диагностика по счётчикам

| счётчик | о чём говорит |
|---|---|
| `fifoOverflow > 0` | пакетов было больше 128: выборка — начало прогона |
| `torn measurements > 0` | пакет догнал предыдущий до завершения его меток. Нормально под нагрузкой, готовые измерения не пострадали |
| `filter RX passed` ≠ числу отправленных | часть кадров не узнана, либо ретрансмиты |

## Чего этот эксперимент не покажет

- **CMAC и кабель** — за врезкой. По даташиту 150–200 нс на сторону
- **приём на половине b** — нужен второй кабель
- **поведение под реальной нагрузкой** — сто пакетов это разовый замер;
  пропускная способность и хвосты требуют другого режима
- **RTT целиком** — его даёт `ppclient`, но там ещё NIC, драйвер и планировщик
  Windows

## Сверка двух измерений

```
RTT(ppclient)  =  2 x [CMAC + кабель + NIC + драйвер + планировщик]
                + TOTAL(pp_measure)
```

Если `RTT - TOTAL` выходит порядка единиц микросекунд — тракт хоста нормальный.
Если десятки — узкое место на PC, а не в плате, и оптимизировать надо там.

## Развилка после замера

**`stack TX` ≈ 100 тактов** → гейтвей ~1.0–1.2 мкс. Для OUCH этого достаточно,
fast path не нужен.

**`stack TX` ≈ 150+** → упираемся в TX-буфер TOE. Его нельзя обойти флагом
(`RX_DDR_BYPASS` работает только на приём), значит потребуется своя логика
передачи — месяцы работы. Решение принимать по числу, не заранее.
