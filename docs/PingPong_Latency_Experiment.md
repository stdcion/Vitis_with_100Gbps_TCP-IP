# Измерение задержки: ping-pong на Alveo U200

Как запустить измерение RTT через echo-ядро и что означают полученные
числа.

> **Статус: план, а не отчёт.** На плате эксперимент ещё не проводился.
> Все числа ниже (`p50`, `35.7 ns`, `44 us`, частота `195.9 MHz`) —
> иллюстрация формата вывода, а не измеренные значения. Не ссылайтесь на
> них как на результат; замените реальными после первого прогона.

---

## Схема

```
┌───────────────────────────┐  100G Ethernet  ┌─────────────────────────┐
│ Хост-клиент               │ ───── TCP ─────>│ FPGA U200               │
│ pingpong_client           │   порт 5001     │ hls_pingpong_krnl       │
│ IP 192.168.1.20           │<─────эхо────────│ IP 192.168.1.10         │
└───────────────────────────┘                 └─────────────────────────┘
     обе стороны — одна подсеть 192.168.1.0/24 (иначе ARP не разрешит MAC)
```

Ядро слушает порт, принимает сообщение и отражает его обратно в ту же
TCP-сессию. Клиент меряет время от `send` до получения эха.

Измеряемый путь целиком:

```
приложение -> send -> драйвер NIC -> провод -> CMAC ->
стек TCP (RX) -> ЯДРО -> стек TCP (TX) -> CMAC -> провод ->
драйвер NIC -> recv -> приложение
```

**Важно:** большая часть RTT — это хост, а не FPGA. Два системных
вызова, прерывания NIC, драйвер и планировщик дают единицы микросекунд.
Вклад ядра — десятки наносекунд (см. раздел про probe).

---

## Два ядра

| ядро                      | что делает                             | когда использовать      |
|---------------------------|----------------------------------------|-------------------------|
| `hls_pingpong_krnl`       | байт-прозрачное эхо                    | обычные замеры RTT      |
| `hls_pingpong_probe_krnl` | эхо + счётчик тактов в первых 4 байтах | чтобы узнать вклад ядра |

Probe-вариант вписывает в начало эха число тактов, которое ядро
потратило на обработку — от прихода уведомления до отправки последнего
слова. Основное ядро остаётся чистым эхом.

Это **отдельные ядра в отдельных каталогах** — так требует Makefile:
он собирает все `.cpp` из `kernel/user_krnl/${USER_KRNL}/src/hls/` в
одну сборку и ищет host в `host/${USER_KRNL}/host.cpp`. Два top-модуля
в одном каталоге дали бы конфликт.

```
kernel/user_krnl/hls_pingpong_krnl/          host/hls_pingpong_krnl/
kernel/user_krnl/hls_pingpong_probe_krnl/    host/hls_pingpong_probe_krnl/
```

Каждое ядро несёт свой `config_sp_<имя>.txt` со связями портов.

## Запуск: базовый замер RTT

### 1. Ядро на FPGA

```bash
source /opt/xilinx/xrt/setup.sh

export DEVICE_1_IP_ADDRESS_HEX_0=C0A8010A      # IP FPGA = 192.168.1.10
export DEVICE_1_MAC_ADDRESS_0=000A35029DE5     # свой MAC

./host ./build_dir.hw.<platform>/network.xclbin 5001
```

Битстрим называется `network.xclbin` независимо от ядра
(`XCLBIN_NAME = network` в Makefile).

Ожидаемо в выводе:

```
Device[0]: program successful!
local IP:c0a8010a, local MAC addr:...
enqueue network kernel...
enqueue pingpong kernel...
Echo kernel is running, listening on port 5001.
```

Ядро free-running (`ap_ctrl_none`) — работает, пока карта
запрограммирована. Host-приложение можно не держать запущенным.

### 2. Клиент

```bash
cd host/hls_pingpong_krnl
gcc -O2 -Wall -o pingpong_client pingpong_client.c -lm

sudo ./pingpong_client 192.168.1.10 5001 64 100000 5000 --cpu 2 --rt
```

Аргументы: `<ip> <порт> <байт> <замеров> <прогрев>`.

`sudo` нужен для `--rt` (SCHED_FIFO).

## Запуск: вклад ядра (probe)

Собрать отдельный битстрим:

```bash
make all TARGET=hw \
  DEVICE=/opt/xilinx/platforms/<platform>/<platform>.xpfm \
  USER_KRNL=hls_pingpong_probe_krnl USER_KRNL_MODE=hls
```

Запустить ядро (host тот же, что у основного, только ищет другое имя
ядра в битстриме):

```bash
./host ./build_dir.hw.<platform>/network.xclbin 5001
```

Затем клиент с `--probe`:

```bash
sudo ./pingpong_client 192.168.1.10 5001 64 100000 5000 --cpu 2 --rt --probe
```

Дополнительно к обычному выводу появится:

```
=== Задержка ЯДРА (счётчик тактов из probe-ядра) ===
частота ядра : 195.9 MHz  (такт = 5.105 ns)
p50   :      7 тактов  (   35.7 ns)
Ядро составляет 0.081% от RTT (p50: 35.7 ns из 44041 ns)
Остальное (44.005 us) — стек TOE, CMAC, провод, NIC и хост
```

Если частота после сборки другая — передайте `--mhz`:

```bash
sudo ./pingpong_client ... --probe --mhz 195.9
```

Актуальную частоту показывает лог сборки:

```
INFO: [v++ 60-1230] ... Kernel (DATA) clock: ss_ucs/aclk_kernel_00 = 195
```

> `--probe` **только** с probe-ядром. С обычным ядром в первых 4 байтах
> лежат данные клиента, и клиент напечатает ошибку с объяснением.

## Опции клиента

| опция        | зачем                                                                  |
|--------------|------------------------------------------------------------------------|
| `--cpu N`    | привязать к CPU N — без этого хвосты (p99) показывают шум планировщика |
| `--rt`       | SCHED_FIFO 80, нужен root                                              |
| `--probe`    | читать счётчик тактов из первых 4 байт                                 |
| `--mhz F`    | частота ядра для пересчёта тактов в наносекунды                        |
| `--verify`   | сверять содержимое каждого сообщения (по умолчанию только на прогреве) |
| `--csv FILE` | куда писать сырые сэмплы (по умолчанию `rtt_ns.csv`)                   |

Клиент печатает блок `=== Измеритель ===` с разрешением таймера и
статусом affinity. Если там `гранулярность` больше 100 нс или
`CPU affinity: нет` — числам в хвостах распределения верить нельзя.

---

## Ограничения

| что                 | значение        | следствие                    |
|---------------------|-----------------|------------------------------|
| размер сообщения    | ≤ **4096 байт** | `PP_MAX_WORDS=64` × 64 байта |
| сессий одновременно | одна            | один клиент за раз           |
| `--probe`           | ≥ 4 байта       | в первых 4 байтах счётчик    |

Ядро store-and-forward: принимает сообщение целиком, потом отправляет.
Поэтому задержка растёт с размером — примерно 2 такта на 64-байтное
слово (приём + отправка).

## Кривая по размеру сообщения

```bash
for SZ in 8 64 256 512 1024 2048 4096; do
  echo "=== msg=$SZ ==="
  sudo ./pingpong_client 192.168.1.10 5001 $SZ 50000 5000 \
       --cpu 2 --rt --csv rtt_$SZ.csv | grep -E "^(min|p50|p99) "
done
```

Ожидаемо: p50 монотонно растёт. Вклад ядра растёт на ~2 такта на слово
(≈10 нс), плюс время передачи на проводе (4096 байт на 100G ≈ 0.33 мкс
в одну сторону).

## Точность измерения

Три вещи сделаны в клиенте намеренно:

**`CLOCK_MONOTONIC_RAW`.** Обычный `CLOCK_MONOTONIC` подстраивается NTP
и на части систем квантует в микросекунды (измерено на macOS:
разрешение 1000 нс против 42 нс у RAW). При RTT в единицы микросекунд
это была бы погрешность ±20%.

**Привязка к CPU и SCHED_FIFO.** Без них планировщик мигрирует процесс,
и p99 показывает не сеть, а шум планировщика.

**Калибровка таймера при старте.** Печатается отдельной строкой —
видно границу собственной погрешности.

> Оверхед таймера **не вычитается** из RTT: `send`/`recv` — неотделимая
> часть измеряемого пути, а не аддитивная поправка.

Для стабильных хвостов дополнительно (вне клиента):

```bash
# изоляция ядра CPU — в /etc/default/grub, затем update-grub + reboot
isolcpus=2 nohz_full=2 rcu_nocbs=2

# частота
sudo cpupower frequency-set -g performance
```

В BIOS отключить C-states и Turbo Boost.

## Что можно и нельзя утверждать

**Можно:**

- сравнивать конфигурации между собой при одинаковых условиях хоста;
- называть вклад ядра — если снято с `--probe`;
- оценивать стабильность по СКО и доле выбросов;
- ловить регрессии, сравнивая с зафиксированным baseline.

**Нельзя:**

- утверждать, что p99 — свойство FPGA, если не сделана изоляция CPU;
- вычитать localhost-замеры из FPGA-замеров (это разные пути, а не
  «тот же плюс сеть»);
- считать, что RTT будет наносекундным — хост даёт микросекунды.
  Наносекунды видны только в счётчике probe.

## Диагностика

| Симптом                       | Причина                         | Решение                                      |
|-------------------------------|---------------------------------|----------------------------------------------|
| Все RTT кратны 1000 нс        | таймер квантует                 | проверить `гранулярность` в выводе           |
| `CPU affinity: нет`           | не передан `--cpu` или нет прав | `--cpu N`, запуск от root                    |
| `SCHED_FIFO: нет`             | нет `CAP_SYS_NICE`              | `sudo`                                       |
| p99 ≫ p50, много выбросов     | хост не подготовлен             | изоляция CPU, governor                       |
| `MISMATCHES`                  | дефект ядра/стека               | прогнать `--verify`, зафиксировать           |
| `ОШИБКА: счётчик ядра >= RTT` | `--probe` с обычным ядром       | собрать probe-ядро или убрать флаг           |
| `connection closed after N`   | сессия закрыта                  | проверить `msg_bytes` ≤ 4096                 |
| `connect: Connection refused` | ядро не слушает                 | проверить, что host запущен и порт совпадает |

## Проверка логики без железа

Обе версии ядра прогоняются в C-симуляции за секунды:

```bash
cd kernel/user_krnl/hls_pingpong_krnl/src/hls
vitis_hls -f run_csim.tcl
```

11 сценариев: эхо, неполное слово (keep), реконнект, серия сообщений,
`tx_status` error==1/2, сообщение больше буфера, сегментация,
усечённый приём, backpressure.

> csim не воспроизводит дедлок по заполнению FIFO — в C-симуляции
> `hls::stream` не имеет ограниченной глубины. Это проверяется только
> co-simulation или на железе.
