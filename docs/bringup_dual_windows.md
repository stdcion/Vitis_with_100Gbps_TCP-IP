# Проверка dual-QSFP на Alveo U200 (Windows + Vivado, JTAG)

Что проверяем: **оба 100G-порта платы работают одновременно и независимо.**

В прошивке один TCP-стек на каждый порт и одно user-ядро, подключённое к обоим
сразу. Ядро echo-типа: принимает TCP-соединение и молча поглощает данные,
ничего не отвечая. Порты слушания **задаются по JTAG**, каждой половине свой.

Критерий успеха: с двух сетевых карт PC одновременно идёт `ping` на оба IP и
устанавливается TCP-соединение к каждому — на свой порт.

Прошивается только конфигурация FPGA. **Flash не трогается** — заводская
прошивка платы остаётся на месте, после выключения питания плата вернётся к ней.

## Что понадобится

| Файл                 | Куда положить           |
|----------------------|-------------------------|
| `net_bd_wrapper.bit` | `C:\net_bd_wrapper.bit` |
| `jtag_ctrl.tcl`      | `C:\jtag_ctrl.tcl`      |

Плюс:

- Vivado (любой 2022.1+, нужен только Hardware Manager),
- USB-кабель JTAG к плате (micro-USB на планке U200),
- плата запитана — U200 требует **дополнительное питание PCIe**, не только слот,
- **оба** QSFP соединены с сетевыми картами PC: DAC-кабелями или трансиверами
  через оптику,
- две пары IP+MAC, свободные в вашем сегменте.

**Какая клетка какая:** QSFP0 — **верхняя**, QSFP1 — **нижняя** (ближе к
краевым контактам PCIe). Так в UG1289, раздел «QSFP28 Module Connector». Легко
перепутать, а симптом будет «порт не работает» на исправной прошивке.

Обе стороны линка должны быть настроены на **100G без RS-FEC** — в прошивке FEC
выключен, и если свитч/NIC его требует, линк не встанет.

## 1. Подключиться к плате

Vivado → **Open Hardware Manager** (Flow Navigator слева, либо
`Flow → Open Hardware Manager`), дальше **Open Target → Auto Connect**.

В панели Hardware появится:

```
localhost (1)
  xilinx_tcf/Xilinx/<серийник>
    xcu200_0 (0)
```

Нет устройства — проверить USB-кабель и питание платы.

## 2. Загрузить битстрим

Правый клик по `xcu200_0` → **Program Device**.

- **Bitstream file**: `C:\net_bd_wrapper.bit`
- **Debug probes file**: оставить пустым

**Program**, занимает ~30–60 секунд.

После загрузки дерево перестроится, и под `xcu200_0` появятся отладочные ядра:

```
xcu200_0 (7)
  hw_axi_1     ← JTAG-to-AXI, через него всё управление
  hw_ila_1     ← ILA на CMAC порта 1
  hw_ila_2     ← ILA на CMAC порта 2
  hw_vio_1     ← VIO стека порта 1
  hw_vio_2     ← VIO стека порта 2
  MIG_1        ← калибровка DDR4
```

**`hw_axi_1` обязателен** — без него скрипт управления работать не будет.

Номера ILA/VIO не гарантированно соответствуют портам. Если нужно точно —
`get_property NAME` покажет путь с `cmac_krnl_1` / `network_krnl_2`.

## 3. Проверить DDR4

Двойной клик по `MIG_1` → таблица стадий калибровки, все должны быть `PASS`.

Или в Tcl Console:

```tcl
get_property STATUS.CAL_STATUS [get_hw_migs]
```

Если калибровка не прошла — дальше идти бессмысленно: TCP-стек держит таблицы
сессий в DDR4. Оба порта используют одну память, так что встанут сразу оба.

## 4. Загрузить скрипт управления

В Tcl Console (внизу окна Vivado):

```tcl
source C:/jtag_ctrl.tcl
```

Слеши **прямые**, даже на Windows — Tcl трактует `\` как escape-символ.

Скрипт только объявляет процедуры, ничего не выполняет. Молчание — нормально.

## 5. Поднять оба порта

Одна команда — сеть и порты слушания сразу:

```tcl
dual_echo_bringup c0a80a0a 000a35029de5 7001 c0a80a0b 000a35029de6 7002
```

Аргументы идут **тройками по интерфейсу**: `IP MAC порт`, сначала QSFP0, затем
QSFP1. IP и MAC — в hex, без `0x` и без разделителей.

| Что | Пример                               | Как перевести                                   |
|-----|--------------------------------------|-------------------------------------------------|
| IP  | `192.168.10.10` → `c0a80a0a`         | каждый октет в hex: 192=c0, 168=a8, 10=0a, 10=0a |
| MAC | `00:0a:35:02:9d:e5` → `000a35029de5` | убрать двоеточия                                |

**IP должны быть разными** — это два независимых стека со своими ARP-таблицами.
MAC любые, лишь бы уникальные в сегменте; локально администрируемые
(`02:00:00:00:00:01`, `02:00:00:00:00:02`) гарантированно ни с чем не столкнутся.

**Порты могут быть одинаковыми**, стеки независимы. Но лучше разные: тогда
неудачное подключение сразу говорит, какая половина виновата, а не оставляет
под подозрением и IP, и порт.

Про подсети: если оба кабеля в одну сеть — оба IP в подсети карты PC. Если в
разные сетевые карты — каждый IP в подсеть своей карты, иначе ОС не поймёт,
через какой интерфейс отвечать.

### Что должно напечататься

```
=== bringup channel 1 (echo) ===
network_krnl: ip=0xc0a80a0a mac=0x000a35029de5
  read back:  ip=0xc0a80a0a mac=0x000a35029de5
  write confirmed
network_krnl[1]: axi00_ptr0=0x00000000 axi01_ptr0=0x40000000
network_krnl[1]: ap_ctrl=0x81 (ap_start=1 ap_done=0)
=== done, channel 1 network is up (IP/MAC latched, stack started) ===

=== bringup channel 2 (echo) ===
...
=== done, channel 2 network is up (IP/MAC latched, stack started) ===

dual_echo[1]: listenPortA=7001 listenPortB=7002
  write confirmed
dual_echo[1]: enable=1
dual_echo[1]: ap_start=1 auto_restart=1 (ap_ctrl=0x81)
  ap_ctrl=0x01 (ap_start=1 ap_done=0)

dual_echo half a: listenAttempts=1 state=2(OPEN) notifications=0
dual_echo half b: listenAttempts=1 state=2(OPEN) notifications=0

Now from the PC (note the port that goes with each IP):
  ncat 192.168.10.10 7001
  ncat 192.168.10.11 7002
```

Три вещи, которые надо увидеть:

- **`write confirmed` три раза** — дважды на сеть, один раз на порты. Скрипт
  читает регистры обратно; если строки нет, JTAG не достучался до платы.
- **`enable=1`** — если вместо этого напечатано `*** enable NOT CONFIRMED`,
  дальше идти бессмысленно: ядро не отвечает на своих регистрах.
- **`state=2(OPEN)` у обеих половин** — порт слушания реально открыт. Это
  главное: раньше этого было не видно, и «порт не открылся» было не отличить от
  «клиент не подключился».

`ap_ctrl=0x81` у `network_krnl` — стек запущен. Там `ap_done` взводится по
таймеру раз в секунду ([network_stack.sv:921](../kernel/network_krnl/src/hdl/network_stack.sv#L921)),
а `auto_restart` (бит 7) тут же переподнимает `ap_start`, поэтому `ap_done=1`
в выводе — не ошибка.

**У user-ядра `ap_ctrl` работу НЕ разрешает.** Разрешает регистр `enable`
(0x10). Ядро объявлено `ap_ctrl_none` и «течёт» с первого такта после снятия
сброса, а `enable` приходит в него проводом из HDL-обёртки и читается каждый
такт. `ap_start` пишется только ради блочного протокола, который ожидает BD, и
как программный сброс счётчиков. Поэтому `ap_done=1` у `dual_echo` тоже
нормально — в обёртке `ap_done = ap_start_pulse`, то есть транзакция
закрывается сразу после старта, не останавливая логику.

### Порядок команд важен

`dual_echo_bringup` делает всё в правильном порядке. По отдельности —
**строго так**:

```tcl
echo_bringup_dual c0a80a0a 000a35029de5 c0a80a0b 000a35029de6
dual_echo_configure 7001 7002
dual_echo_enable 1
```

`enable` **последним**. Ядро работает с первого такта после загрузки битстрима,
поэтому до разрешения хоста оно не трогает стек: порты могут быть ещё не
записаны, а сам стек — не запущен. Запрос listen раньше времени уходит в стек,
у которого ещё нет IP.

## 6. Проверка с PC

Сначала ARP и IP на каждом порту:

```
ping 192.168.10.10
ping 192.168.10.11
```

ARP отвечает сам стек на плате. Идут оба ping — поднялись оба 100G-линка, оба IP
прописались.

Дальше TCP, **каждый на свой порт**:

```
ncat 192.168.10.10 7001
ncat 192.168.10.11 7002
```

(или PowerShell `Test-NetConnection 192.168.10.10 -Port 7001`)

**Оба соединения установились и держатся — эксперимент удался.** Ответа не
будет: ядро принимает и сбрасывает данные, обратно ничего не отправляет. Сам
факт установления соединения и есть результат.

Главная проверка — держать **оба** соединения открытыми одновременно, в двух
окнах, и полить в каждое данными. Порты не имеют общего состояния: обрыв или
зависание на одном не должны влиять на второй.

Что данные дошли до ядра, видно по счётчику:

```tcl
dual_echo_status
```

`notifications` растёт — ядро получает уведомления о данных.

## Если не работает

**Ни один ping не идёт.** Двойной клик по `hw_vio_1`, добавить пробы —
смотреть `stat_rx_status` и `stat_rx_aligned`. Если `rx_aligned = 0`, линк не
поднялся физически: проверить кабель, трансиверы и что вторая сторона на 100G
**без RS-FEC**. Это самая частая причина.

**Ping идёт на один порт, но не на второй.**

1. `hw_vio` второго порта → `stat_rx_aligned`. Если 0 — линк не встал.
2. Переставить рабочий кабель в проблемную клетку. Заработало — дело в кабеле
   или трансивере.
3. Не заработало — сообщите нам, приложив состояние `stat_rx_*` из VIO.

**Ping идёт на оба, TCP не подключается.** Смотреть `dual_echo_status`:

| что видно | что это значит |
|---|---|
| `state=0(wait-enable)` | `dual_echo_enable 1` не вызывался |
| `state=1(requested)`, `listenAttempts` растёт | стек не отвечает на запрос listen. Проверить, что bringup сети шёл **до** `enable` |
| `state=2(OPEN)` | порт открыт — проверьте, что подключаетесь на **тот** порт (у половин они разные) |

**`write confirmed` нет после `dual_echo_configure`, или
`*** enable NOT CONFIRMED`.** Ядро не отвечает по JTAG на этих регистрах.
Причины, по убыванию вероятности:

1. прошит битстрим, собранный **без шага 2.5** (упаковки HDL-обёртки) — тогда
   у ядра нет регистров управления вовсе. Признак в логе сборки BD:
   `user-ядро: сырое HLS-IP` вместо `HDL-обёртка`;
2. смещения `DE_OFF_*` в скрипте разошлись с прошивкой. Источник истины —
   блок `localparam` в
   [dual_echo_control_s_axi.v](../kernel/user_krnl/hls_dual_echo_krnl/src/hdl/dual_echo_control_s_axi.v);
3. база адресов не та — сверить с `ouch_base_user` в скрипте и выводом
   `=== адреса s_axi_control ===` из лога сборки BD.

Сообщите нам вывод.

**Работает только тот порт, который поднят последним.** Так бывает, если
поднимать сеть вручную через `network_configure` без `network_set_buffers` —
тогда стеки получают пересекающиеся области в DDR4 и затирают друг другу
таблицы сессий. `dual_echo_bringup` и `echo_bringup_dual` разносят их сами
(канал 1 → `0x0/0x40000000`, канал 2 → `0x80000000/0xC0000000`), поэтому
пользуйтесь ими.

**Открылась ровно одна половина, вторая в `state=1(requested)`.** Если при
этом ping идёт на оба IP и `stat_rx_aligned=1` на обоих портах, дело не в
линке. Соберите вывод `dual_echo_status` и сообщите: половины должны иметь
раздельное состояние по построению, и такой симптом означал бы, что они его
делят.

**После выключения платы всё пропало.** Так и задумано, конфигурация FPGA
волатильная. Повторить шаги 2–5.

## Повторная загрузка

Программировать заново можно сколько угодно — `Program Device` перезаписывает
конфигурацию. После каждой перепрошивки заново шаги 4–5 (`source` и
`dual_echo_bringup`): регистры сбрасываются вместе с логикой.

**Повторный `dual_echo_bringup` без перепрошивки IP не сменит.** Стек
защёлкивает адреса только по фронту `ap_start`, а `auto_restart` держит его
поднятым — фронта больше не будет. Меняете IP — перепрошейте плату.

## Что сообщить о результате

- идут ли `ping` на оба IP;
- вывод `dual_echo_bringup` целиком;
- `dual_echo_status` — `state` и `notifications` по обеим половинам;
- устанавливаются ли оба TCP-соединения, и держатся ли **одновременно**;
- если что-то не поднялось — `stat_rx_aligned` и `stat_rx_status` из
  `hw_vio_1`/`hw_vio_2` по каждому порту.
