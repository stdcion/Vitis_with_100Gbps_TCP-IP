# Эксперимент 1: работает ли TCP-эхо на U200

**Что проверяем: отдаёт ли плата данные обратно в сеть.**

Это первый раз, когда TX-путь стека TOE вообще задействован. Все зелёные
результаты до сих пор — приёмники: фазы 1–3 лестницы `hls_recv_dual_krnl`
прошли с `tie_off_tcp_tx` на обеих половинах, то есть передача не проверялась
ни разу.

**Критерий успеха:** отправленная строка возвращается обратно.

Врезки времени в этом эксперименте **не участвуют** — они собраны в прошивке, но
измерения снимаются во втором заходе. Здесь один вопрос: работает ли эхо.

## Почему это отдельный эксперимент

В одной попытке смешивать «работает ли эхо» и «верны ли мои измерения» нельзя:
при отказе не различить, что именно сломалось. Сначала подтверждаем эхо, потом
меряем.

## Схема

```
        PC (Windows)                     Alveo U200
    ┌──────────────┐               ┌──────────────────────┐
    │  ppclient    │  ── TCP ──►   │ QSFP0 → CMAC0 →      │
    │  192.168.10.1│               │   network_krnl_1 →   │
    │              │  ◄── эхо ──   │     pp_echo          │
    └──────────────┘               │                      │
                                   │ QSFP1: без кабеля    │
                                   └──────────────────────┘
```

Половина b (QSFP1) в прошивке есть и слушает, но кабеля в ней нет. Она
оставлена, чтобы отличие от зелёной фазы 3 было минимальным: уберём — и при
отказе придётся выяснять, не в этом ли дело.

## Что понадобится

| Файл                 | Куда                    |
|----------------------|-------------------------|
| `net_bd_wrapper.bit` | `C:\net_bd_wrapper.bit` |
| `jtag_ctrl.tcl`      | `C:\jtag_ctrl.tcl`      |
| `ppclient.exe`       | `C:\ppclient.exe`       |

`ppclient.exe` собирается на любой машине с Go:

```sh
cd host/hls_pp_dual_krnl && ./build.sh
```

Даёт `bin/ppclient.exe` — статический бинарник, на Windows не нужны ни Go, ни
runtime, ни DLL.

Плюс: Vivado (нужен только Hardware Manager), USB-кабель JTAG, дополнительное
питание PCIe, **один** DAC-кабель или трансивер из QSFP0 в сетевую карту PC.

## Адреса

|                                | IP                            | MAC                 |
|--------------------------------|-------------------------------|---------------------|
| половина a (QSFP0, кабель)     | 192.168.10.10                 | `02:aa:00:00:00:01` |
| половина b (QSFP1, без кабеля) | 192.168.10.20                 | `02:bb:00:00:00:02` |
| сетевая карта PC               | 192.168.10.1 или любой из /24 | —                   |

Порт слушания: **7001** на обеих половинах. Конфликта нет — разные стеки,
разные IP, две независимые сессии.

Эти адреса взяты из зелёной фазы 3: на них лестница прошла на плате 25.08,
значит ARP, маска подсети и gateway с ними заведомо работают.

## Порядок

### 1. Прошить

Hardware Manager → `Program Device` → `C:\net_bd_wrapper.bit`.

Прошивается только конфигурация FPGA, flash не трогается.

### 2. Поднять стеки и ядро (Tcl Console в Vivado)

```tcl
source C:/jtag_ctrl.tcl
pp_dual_bringup
```

**Что смотреть в выводе:**

| строка                  | значение                                       |
|-------------------------|------------------------------------------------|
| `register map: ...hw.h` | карта регистров ядра прочитана                 |
| `write confirmed`       | `useConn`/`basePort` доехали                   |
| `ap_ctrl=0x81`          | `ap_start=1`, `auto_restart=1` — ядро запущено |
| `portState`             | **должно стать 2**                             |

`portState` — первая точка отказа. Если 0 или 1, порт не открылся, и дальше идти
незачем: смотрите `pp_taps_status` и вывод `echo_bringup` для обоих каналов.

### 3. Захват на PC — ДО отправки

Wireshark на QSFP-интерфейс, display filter:

```
tcp.port == 7001
```

Это единственный источник правды, не зависящий от нашей телеметрии. Телеметрия
уже вводила в заблуждение: `ap_ctrl=0x83` читалось как «залип», а это был
sticky-бит «финишировал хоть раз».

### 3.5. Проверить линк: ping

```
ping 192.168.10.10
```

**Первый пакет теряется всегда — это нормально.** `mac_ip_encode.cpp:176-181`
при промахе в ARP-таблице кадр **отбрасывает**, а не откладывает до ответа:

```cpp
if (reply.hit) { /* отправляем */ }
else { if (!word.last) har_state = DROP; }   // молча выбрасываем
```

Порядок: приходит echo request → стек готовит reply → спрашивает MAC → записи
нет → **reply отброшен**, уходит ARP-запрос → PC отвечает → второй ping идёт.

ARP при этом отвечает сразу, потому что ARP-ответ идёт через `mac_merger`
(`network_stack.sv:546`) в обход `mac_ip_encode` — ему таблица не нужна.

Так одинаково на рабочих и нерабочих сборках. Судить по второму и последующим:
идут — линк, IP, ARP в порядке. Не идут вообще — проблема в линке, и до TCP
дело не доходит.

### 4. Дым-тест: сто сообщений

```
ppclient.exe -host 192.168.10.10 -port 7001 -count 100
```

Начинать со ста, а не со ста тысяч: при отказе не тратить время.

### 5. Счётчики обратно в Vivado

```tcl
pp_taps_status
```

## Как читать результат

### Успех

```
200 samples, 64 bytes
min        :      3200 ns  (  3.200 us)
p50        :      3800 ns  (  3.800 us)
...
```

Эхо вернулось. **TX-путь стека работает** — то, чего мы не знали с начала
работы. Дальше имеет смысл второй заход с измерениями.

Порядок величины ждём микросекунды. Оценка бюджета (`docs`,
`toe-latency-budget-estimate`): RTT 2.3–3.6 мкс, из них гейтвей 1.0–1.8. Если
выйдет 50+ мкс — это не задержка железа, а Нейгл или что-то в тракте хоста;
клиент ставит `TCP_NODELAY`, но стоит проверить настройки NIC.

### `connection refused`

Порт не открыт. `portState` покажет:

| значение | что значит                                                      |
|----------|-----------------------------------------------------------------|
| 0        | listen не запрашивался — стадия не работает, смотрите `ap_ctrl` |
| 1        | запрос отправлен, стек не подтвердил                            |

### Соединение есть, эха нет

```
no echo after 0 msgs: i/o timeout
connected but silent -- read ppState via pp_dual_dump
```

Значит SYN-ACK пришёл (listen работает), а данные не вернулись. Читайте
`ppState` — он назовёт шаг, на котором встало:

| `ppState` | шаг    | что не случилось                                     |
|-----------|--------|------------------------------------------------------|
| 0         | NOTIFY | уведомление о данных до ядра не дошло                |
| 1         | META   | `read_pkg` отправлен, `rx_meta` не пришла            |
| 2         | RX     | слова идут, `tlast` не пришёл                        |
| 3         | REQ    | не пишется `tx_meta` (транзитное, видеть не должны)  |
| 4         | STATUS | **стек не ответил на `tx_meta` — TX-путь достигнут** |
| 5         | TX     | слова не принимаются, backpressure                   |

`ppState = 4` — самый информативный исход при отказе: он означает, что ядро
дошло до передачи и стек не ответил. `tasi_metaLoader` отвечает на **каждый**
`tx_meta` (`tx_app_stream_if.cpp`), так что молчание указывает на состояние
сессии, а не на наш код.

### Тишина на SYN

Ни SYN-ACK, ни RST. То же, что было у `dual_echo` — но теперь есть `portState`
и `ppState`, которые различают причины.

### `*** N MISMATCHES`

Эхо вернулось, но данные не совпали. Дефект ядра: `keep` последнего слова,
границы `payload[]`, `txLength` в `pp_echo`. Измерение при этом бессмысленно.

## Что этот эксперимент не проверяет

- **приём на половине b** — нужен второй кабель, а мощность перетыканий
  ограничена
- **задержку по участкам** — врезки собраны, но снимаются вторым заходом
- **работу под нагрузкой** — сто пакетов это проверка факта, не пропускной
  способности

## Если понадобится без ppclient

Любой TCP-клиент подойдёт для дым-теста:

```
telnet 192.168.10.10 7001
```

Набрать строку, Enter — должна вернуться. Но **маркер в payload не будет
записан**, поэтому фильтр кадров наш пакет не узнает, и счётчики
`pp_taps_status` останутся нулевыми. Для факта «эхо есть» этого хватает, для
измерений — нет.

## Что делать после

**Эхо работает** → второй заход: `pp_measure`, разбивка задержки по участкам
(приём стека / ядро / передача стека).

**Эхо не работает** → `ppState` указал шаг. Дальше читаем код этого шага, а не
гадаем: за прошлую неделю девять гипотез были отброшены измерением, и все были
о том, чего не видно.
