# Контрольный опыт recv_dual: отделить СХЕМУ от ЛОГИКИ

Состояние на 20.08.2026. Файл описывает опыт, который ставится сейчас, и то,
что к нему привело. Предыдущий контекст —
[kernel_scheme_handoff.md](kernel_scheme_handoff.md) (дерево гипотез по
dual_echo и probe) и [latency_session_handoff.md](latency_session_handoff.md)
(врезки, методика, пять дефектов HLS).

## Зачем опыт

`hls_dual_echo_krnl` не работает, `hls_recv_krnl` работает. Но они отличаются
СРАЗУ ДВУМЯ вещами, и потому отказ dual_echo не называет виновного:

| | A. Схема | B. Логика |
|---|---|---|
| `hls_recv_krnl` | один `network_krnl`, 16 портов | upstream `listenPorts` + `recvData` |
| `hls_dual_echo_krnl` | ДВА `network_krnl`, 32 порта на инстанс | свои FSM с early `return` |

`hls_recv_dual_krnl` меняет **только A**, оставляя B заведомо рабочей.

## Что доказал захват Wireshark (20.08)

Это самое твёрдое, что есть в деле, и получено без единой гипотезы про HLS.

| ядро | порт | результат |
|---|---|---|
| `hls_recv_krnl` | 7001 | **SYN-ACK за 69 мкс**, соединение установлено (`Conversation completeness: Complete`) |
| `hls_recv_krnl` | 7005 / 7007 | **RST за 64–66 мкс** — закрытый порт, верно |
| `hls_dual_echo_krnl` | 7001 | **тишина**, ретрансмиты SYN |

**Тишина и RST — разные ветки `rx_engine`, и это локализует дефект точно.**
`rx_engine.cpp:876`:

```cpp
if (!portIsOpen) {
    // SEND RST+ACK           <- 7005/7007
} else {
    rxEng2sLookup_req.write(sessionLookupQuery(tuple, syn && !rst && !fin));
    mh_state = LOOKUP;         <- dual_echo/7001 идёт СЮДА
}
```

Раз dual_echo не получает RST — **порт зарегистрирован**, listen отработал.
Дальше в `LOOKUP` (`:914`) при `!hit` **не делается ничего**: ни ответа, ни RST.
Закомментированный блок ниже это признаёт: `// Port is Open, but we have no
sessionID... For SYN we should time out, for everything else sent RST TODO`.

Значит промах lookup'а роняет SYN беззвучно — ровно наблюдаемый симптом.

## Что опровергнуто по дороге (не проверять заново)

| гипотеза | чем закрыта |
|---|---|
| SYN-ACK уходит на `0.0.0.0` | захват: адрес правильный, `192.168.10.1` |
| таблица сессий в DDR, путь к памяти сломан | `session_lookup_controller.cpp:254` — `bind_storage impl=BRAM`, ни одного `m_axi` в файле; в DDR только буферы данных, handshake нулевой длины их не трогает |
| `myIpAddress` у ARP расходится с VIO | `network_stack.sv:275-277` — безусловное присваивание из `local_ip_address`, разойтись не может |
| барьер `ap_sync_done` держит регион | `hls_dual_echo_krnl.v:840` — `assign dual_echo_core_U0_ap_continue = 1'b1` |
| `ap_start` не доходит до региона | `:842` — `assign dual_echo_core_U0_ap_start = ap_start` |
| `static` теряется при `auto_restart` | `dual_echo_listen.v:355,365,375` — сброс ТОЛЬКО по `ap_rst` |
| мониторы дедлока указывают на канал | шаблонные; `idx1` — контейнер, инстанцирующий остальные 12 |
| гонка инициализации / невоспроизводимость | recv использует тот же порядок bringup и работает |

**Осторожно с `arp_rx`.** Счётчик VIO (`probe_in11`) считает кадры на ВХОДЕ в
`arp_server`, ДО проверки адреса (`network_stack.sv:1113`). Счётчик после
матча — `arp_request_pkg_counter` — на VIO не выведен. Поэтому «`arp_rx` растёт,
`arp_tx` стоит» НЕ обвиняет ARP-сервер. Стоит добавить его в пробы.

## Лестница: по одному изменению за шаг

| шаг | что меняется | ожидание | статус |
|---|---|---|---|
| **0** | копия recv, ноль правок | работает | `75b4652`, откат |
| **1** | +16 портов канала `b` на `tie_off_*` | схема исправна | `917706d`, **собирается** |
| **2** | канал `b`: кабель, IP/MAC, старт стека; слушать не слушаем | физика двух CMAC | `46a3ed3`, код не меняет |
| **3** | `listenPorts`+`recvData` на обеих половинах | цель: dual-QSFP на upstream | не начат |
| **4** | свои стадии по одной | первый отказ назовёт виновную | не начат |

Шаг 3 — то, ради чего затевался dual_echo: рабочее dual-QSFP ядро БЕЗ единой
своей стадии. Шаг 4 — место, где вскроется настоящая причина, скорее всего на
`rx_notify` с его двумя `return`.

## Что сделано и чем проверено

`kernel/user_krnl/hls_recv_dual_krnl/` — ядро и `config_sp_..._dual.txt`.

Отличие от эталона `hls_recv_krnl` — **ровно одно**: 16 портов канала `b`, все
закрыты заглушками. Логика канала `a` не тронута ни строкой.

Сверено машиной, не глазами:

| проверка | результат |
|---|---|
| канал `a` в `config_sp` vs рабочий recv | **diff пустой**, построчно |
| порты `config_sp` ↔ `.cpp`, В ОБЕ СТОРОНЫ | 32 = 32, ни лишних, ни забытых |
| связей на канал | 18, как у dual_echo |
| `g++ -fsyntax-only` через csim-шим | чисто |
| синтаксис `jtag_ctrl.tcl` | `tclsh`: `info complete` + `eval` |

`config_sp` сделан СТРУКТУРНОЙ копией dual_echo (те же `network_krnl_1/2`,
`cmac_krnl_1/2`) — иначе результат не переносился бы на dual_echo.

### ДВА network_krnl, ОДНО пользовательское ядро

Это разные вещи, и путать их дорого:

* `network_krnl_1`, `network_krnl_2` — **два** инстанса, стек на каждый QSFP.
  Каждому свой IP/MAC и свой `network_start` → `echo_bringup` на n=1 и n=2.
* `hls_recv_dual_krnl_1` — **один** инстанс, подключён к ОБОИМ стекам
  (`build_bd.tcl:369` против `:358-360`). `recv_start` делается ОДИН раз;
  по `ouch_base_user 2` пользовательского ядра нет, там DECERR.

## Сборка

```bash
make -f Makefile.vivado all USER_KRNL=hls_recv_dual_krnl BOARD=u200
```

`NUM_QSFP` указывать не нужно: по умолчанию 2 (`Makefile.vivado:123`), а
`build_bd.tcl:79` сам падает, если dual-ядру дали `NUM_QSFP=1`. Dual-режим
включается по наличию `config_sp_<krnl>_dual.txt`.

### До платы — подтвердить карту регистров

Порты добавлены ПЕРЕД скалярами; `hls::stream` в control-карту не попадают, так
что смещения должны сохраниться — но это надо увидеть, а не принять на веру:

```bash
grep -n "USECONN\|BASEPORT\|RXBYTE" \
  kernel/user_krnl/hls_recv_dual_krnl/src/hls/hls_recv_dual_krnl_ip_proj/sol1/impl/ip/drivers/hls_recv_dual_krnl_v1_0/src/xhls_recv_dual_krnl_hw.h
```

Ждём `0x10` / `0x18` / `0x20` — тогда `recv_start` работает без правок.

## Запуск на плате

```tcl
source C:/jtag_ctrl.tcl
recv_dual_phase1          ;# канал b тёмный
recv_dual_phase2          ;# оба стека подняты, слушает только a
recv_dual_vio             ;# счётчики обоих каналов
```

С хоста: `ncat 192.168.10.10 7001`.

### Как читать результат

| наблюдение | вывод |
|---|---|
| handshake проходит | **СХЕМА ИСПРАВНА** → виновата логика dual_echo, дальше шаг 3 |
| тишина, ретрансмиты | схема ломает → но сначала проверить ловушку ниже |

В фазе 2 дополнительно:

| наблюдение | вывод |
|---|---|
| `a` соединяется, `b` даёт **RST** | схема чиста под нагрузкой |
| `a` замолчал | сломал второй живой стек (сравнить с фазой 1, где `b` тёмный) |
| `b` молчит **вместо RST** | канал `b` не получил IP → `recv_dual_vio` |

Третья строка важна: на `b` никто не слушает, поэтому RST — ПРАВИЛЬНЫЙ ответ.
Тишина там означала бы, что стек `b` не поднялся.

### ЛОВУШКА при тишине: заглушки — тоже стадии

Было **6** стадий, стало **12** (посчитано по вызовам, не на глаз).
`ap_sync_done` — это И по `ap_done` ВСЕХ стадий
(`hls_dual_echo_krnl_dual_echo_core.v:1347`). Поэтому причиной тишины может
оказаться разросшийся регион, а НЕ схема — и тогда опыт обвинит схему ложно.

**КРИТЕРИЙ ИСПРАВЛЕН 20.08 -- прежний был неверен.** Здесь стояло: «единица (как
у dual_echo) -> барьер никого не держит». Проверка на собранном `recv_dual`
показала `ap_continue = ap_sync_done` у всех 12 стадий, что по прежнему критерию
означало бы взведённый барьер и ложное обвинение схемы.

Сверка с RTL **работающего** `recv` (распакован из `recv_rtl.tgz`):

| | стадий | `ap_continue` |
|---|---|---|
| `recv` (работает) | 6 | `ap_sync_done` у всех |
| `recv_dual` | 12 | `ap_sync_done` у всех |

Форма ИДЕНТИЧНА, значит `ap_sync_done` сам по себе ни о чём не говорит.

**Барьер мёртв, если хотя бы одна стадия НИКОГДА не финиширует** -- тогда
`ap_sync_done` вечно 0 и `ap_continue` никого не отпускает, но и не нужен. У
upstream именно так: `recvData_handshake` -- `do/while` по счётчику байт, из него
не выходят (`communication.hpp:1239`). Заглушки этого не меняют: они финишируют,
а `recvData` -- нет, а барьер это И по ВСЕМ.

`recv_dual` использует ТЕ ЖЕ upstream-стадии -> барьер мёртв так же, как у
`recv`. Разросшийся регион причиной тишины быть НЕ МОЖЕТ, и обвинение схемы
будет честным без дополнительных проверок.

Проверить при необходимости:

```bash
grep -n "assign ap_sync_done = " \
  kernel/user_krnl/hls_recv_dual_krnl/src/hls/hls_recv_dual_krnl_ip_proj/sol1/syn/verilog/hls_recv_dual_krnl.v
```

В списке должна быть `recvData_U0_ap_done` -- она и держит барьер мёртвым.

## Ограничения стенда — учитывать при планировании

| ограничение | следствие |
|---|---|
| плата ~10 минут в день, удалённо, командами человеку у платы | прибор для снятия данных, не отладочный стенд |
| ILA неприменим | всё диагностируется РЕГИСТРАМИ и захватом с хоста |
| ресурс перетыканий QSFP ограничен | фаза 1 кабель во второй порт НЕ требует |

## Где искать пути

HLS-проект лежит **в дереве исходников**, не под `build/`
(`export_hls_ip.tcl:98`), и все файлы префиксованы именем топ-функции:

```
kernel/user_krnl/<krnl>/src/hls/<krnl>_ip_proj/sol1/syn/verilog/<krnl>_<stage>.v
```

Имена брать из вывода `find`, а не достраивать по догадке.
