## 0. Перед началом: физика стенда

**Кабель между QSFP0 и QSFP1 самой платы.** Не к PC. Клиент на порту 0 ищет
сервер на порту 1 через провод, поэтому нужна петля.

QSFP0 — **верхняя** клетка, QSFP1 — **нижняя** (ближе к контактам PCIe).
Перепутать легко, а симптом — «соединение не открылось» на исправной прошивке.

По handoff кабель сейчас воткнут только в QSFP1 — **это надо исправить до
запуска**, иначе probe не заработает в принципе.

`ping` с PC не пойдёт и не должен: порты соединены друг с другом. Физику
проверяем по `stat_rx_aligned` в VIO.

## 1. Сборка (сборочная машина, ~1.5 часа)

```bash
cd ~/easynet && git pull
```

Прогнать проверки до сборки — минута, а impl час:

```bash
cd kernel/user_krnl/hls_echo_probe_dual_krnl/src/hdl/tb && ./run_sim.sh
cd ../../hls && vitis_hls -f run_csim.tcl
cd ~/easynet && tclsh scripts/vivado/test_epd_taps.tcl
```

Ждём `ALL GREEN` во всех трёх тестбенчах, `failures=0` в csim и `ВСЁ ЗЕЛЁНОЕ` в
tcl-тесте. Если что-то красное — **не собирать**, разбираться.

Дальше четыре шага. Первый (`xo`) нужен, только если `cmac_krnl`/`network_krnl`
ещё не собраны на этой машине:

```bash
cd ~/easynet
make -f Makefile.vivado xo      BOARD=u200 NUM_QSFP=2                              # ~1 мин, если ещё не собрано
make -f Makefile.vivado user_ip USER_KRNL=hls_echo_probe_dual_krnl BOARD=u200      # ~20 с
make -f Makefile.vivado pack    USER_KRNL=hls_echo_probe_dual_krnl BOARD=u200      # ~1 мин
make -f Makefile.vivado bd      USER_KRNL=hls_echo_probe_dual_krnl BOARD=u200 NUM_QSFP=2   # ~25 с
make -f Makefile.vivado impl    USER_KRNL=hls_echo_probe_dual_krnl BOARD=u200 JOBS=1 2>&1 | tee ~/impl_probe.log
```

`JOBS=1` не случайно: при `JOBS=4` был OOM на 30 ГБ.

### Что смотреть в логах

**После `pack`** — строку про врезки:

```
врезки axis_net_*: все 8 интерфейсов распознаны
```

Если её нет — упаковка упадёт сама с объяснением. Это проверка, что Vivado вывел
шинные интерфейсы из имён портов; без неё BD упал бы позже и невнятно.

**После `impl`** — три числа:

```bash
grep -E "@@@|12-2285|Common 17-55|Place 30-1241" ~/impl_probe.log
```

* **WNS** — главное. **Это единственное, чего не проверила симуляция.** Запас до
  врезок был +0.0858 нс. Врезки логику в тракт не добавляют (`tdata` идёт
  насквозь чистыми `assign`, фильтр висит ответвлением), но fanout и путь до
  триггера фильтра появились.
* `12-2285`, `Common 17-55`, `Place 30-1241` — ждём нули.

**Если WNS ушёл в минус** — по handoff план такой: врезок поставлено сразу
четыре, поэтому виновную не видно. Откатывать до одной (только `T1'` на
`tx_a`), это даст `STACK_0_TX` и покажет, тайминг ли вообще проблема.

## 2. Прошивка и bringup (Windows + Vivado, JTAG)

Скопировать на машину с платой:

* `net_bd_wrapper.bit` из `build/vivado/u200/hls_echo_probe_dual_krnl/net_vivado.runs/impl_1/`
* `scripts/vivado/jtag_ctrl.tcl`

В Hardware Manager: `Open target → Auto Connect`, затем `Program Device` этим
битстримом. Flash не трогаем — после выключения плата вернётся к заводской.

Дальше в Tcl-консоли Vivado:

```tcl
source C:/jtag_ctrl.tcl
echo_bringup_dual 0a01d498 020000000001 0a01d499 020000000002
```

Требования к адресам жёсткие, иначе ARP не разрешится:

* **оба IP в одной подсети /24** — в стеке `IP_DEFAULT_GATEWAY = 0`;
* **последние октеты обязаны различаться** — ARP-таблица индексируется одним
  октетом, вторая запись затрёт первую;
* MAC лучше локально администрируемые (`02:...`).

## 3. Измерение

```tcl
epd_calibrate                        ; # сколько стоит JTAG-транзакция
epd_configure 0a01d499 7001 64       ; # server ip, порт, размер сообщения
epd_enable 1                         ; # ВСЕГДА последним, после configure
epd_status                           ; # соединение открылось?
epd_net_status                       ; # ЖИВЫ ЛИ ВРЕЗКИ — до первого замера
epd_measure                          ; # один замер целиком
epd_collect 20                       ; # статистика
```

Порядок важен в двух местах. `epd_enable` — **после** `epd_configure`: до
разрешения ядро не трогает порты стека, и это защита от гонки со стеком.
`epd_net_status` — **до** `epd_measure`: иначе «нули в таймстемпах `T`» не
отличить от «врезка подключена не туда».

### Три места, где можно застрять

**`epd_configure` говорит `minWords NOT CONFIRMED`** — загружен битстрим без
врезок. `msgBytes` при этом пишется верно. Пересобрать.

**`epd_status`: `state=1`, а не `2(OPEN)`** — порт слушания не открылся. Скрипт
сам подскажет, куда смотреть; чаще всего `echo_bringup_dual` не прогнали до
`epd_enable`.

**`epd_net_status`: `passed=0 dropped=0` на обоих каналах** — врезки не видят
трафика вообще. Либо битстрим старый, либо `config_sp` не развернул `axis_net_*`
через обёртку.

`passed=0`, а `dropped` растёт — смотреть на `sent` в той же строке:

* **`sent=0`** — это НОРМА, а не отказ. До первого замера по проводу прошли
  только ARP и SYN/SYN-ACK, а их фильтр и должен отсеивать. Скрипт так и
  напишет. Перепроверить после `epd_measure`.
* **`sent>0`** — вот теперь фильтр режет всё, включая наш кадр: `minWords`
  завышен, перезапустить `epd_configure`.

### Что читать в `epd_measure`

Семь слагаемых круга плюс строка `residual`. Она единственная здесь **не
тождество**, поэтому несёт информацию:

* **такт-два** — норма. Это разница путей штамповки: точки `t` идут через
  `ap_vld` зарегистрированного выхода HLS, точки `T` — прямо с шины. Эта
  константа потом вычитается из четырёх `STACK_*`.
* **десятки тактов** — фильтр защёлкнулся на чужом кадре. Тогда
  `epd_net_status` и раздел «Чужой трафик на шине» в
  [latency_net_probe_design.md](latency_net_probe_design.md).

`EXT_A`/`EXT_B` ожидаются в единицы-десятки тактов. Сотни — тот же диагноз.

## 4. Свип и выгрузка

```tcl
foreach sz {64 128 256 512 1024 1500} {
     epd_configure 0a01d499 7001 $sz
     set fh [open C:/epd_raw_$sz.csv w]
     puts $fh [epd_raw 20]
     close $fh
     puts "--- $sz bytes done ---"
}
```

Порог фильтра `epd_configure` пересчитывает сам, пересборка не нужна.
`msgBytes < 32` скрипт отвергает: ниже фильтр не отличает наш кадр от ACK.

**По времени:** замер стоит 10 JTAG-транзакций (было 6 до врезок). При 10 мс на
транзакцию это ~100 мс на замер, `epd_collect 20` — около двух с половиной
минут, весь свип — минут пятнадцать.

## 5. Что прислать

* вывод `epd_calibrate`, `epd_status`, `epd_net_status`;
* `epd_measure` целиком — обе строки `raw` и строку `residual`;
* сводки `epd_collect 20` по каждому размеру;
* файлы `epd_raw_*.csv`;
* из лога сборки — строки `@@@` с WNS;
* если не поднялось — `echo_bringup_dual` целиком и `vio_dump`.

## Чего этот эксперимент не покажет

Стоит держать в голове, читая первые числа:

* **задержку до биржи** — только вклад FPGA;
* **вклад логики гейтвея** — она не написана, `ECHO` почти ноль. Мы меряем
  «пол», ниже которого гейтвей не опустится;
* **встречную нагрузку** — в эхо-схеме запрос и ответ разнесены во времени, а в
  бою оба стека конкурируют за общий DDR4 одновременно;
* **retransmit и потери** — в loopback их нет, а в бою они дают редкие большие
  выбросы, то есть тот самый хвост, который в HFT и решает.

Отдельно: **ARP-резолв симуляция не проверяла вообще** — модель стека в
тестбенче доставляет пакеты напрямую. На плате он случится первый раз именно
здесь, и симптом отказа — растущий `connAttempts` при нулевом `sent`.
